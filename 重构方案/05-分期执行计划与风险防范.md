# 05-分期执行计划与风险防范

## 1. 目标与执行原则

本文件是前四份专项方案的阶段总控文档，目标不是重复架构设计，而是把重构落成一套可执行、可验收、可回滚的阶段计划。

当前已经确认的总方向不是“长期兼容双跑”，而是：

- 对内：阶段化重建
- 对外：新前端 + 新 API + 新数据层 + 新工作流一次切换

因此，本文件必须与 `00-重构总控与并行执行总览.md`、`12-Subagent-并行执行协议.md`、`13-前端完整重构方案.md`、`14-后端完整重构方案.md` 一起阅读，不能单独解读为“最终形态仍保留兼容层和旧前端”。

执行原则固定为 6 条：

1. 主事实源切换永远晚于投影切换。
2. 先冻结 contracts 与迁移基线，再建新写路径与新读模型，最后再做正式切换。
3. 任何阶段都必须有明确的入口条件、退出条件和回滚条件。
4. 不允许“边重构边偷改语义”；单世界、canon/candidate、draft/review 等核心语义必须先冻结。
5. workflow、存储、接口三条线必须分开验收，不能一次性一起切。
6. 删除旧 JSON/SQLite 写路径只能发生在迁移 rehearsal、故障演练与回滚演练全部通过之后。

本计划现在强依赖以下补充文档，没有这些文档，任何“全功能完整迁移”声明都无效：

- `00-重构总控与并行执行总览.md`
- `06-全功能盘点与迁移对照矩阵.md`
- `07-全接口与前端页面覆盖清单.md`
- `08-旧数据逐字段映射与迁移脚本规范.md`
- `09-功能等价验收与回归测试矩阵.md`
- `10-隐性语义与底层兼容矩阵.md`
- `11-Graph-重构路径与验收方案.md`
- `12-Subagent-并行执行协议.md`
- `13-前端完整重构方案.md`
- `14-后端完整重构方案.md`

## 2. 分期执行总览

| Phase | 阶段名称 | 核心目标 | 主要产出 | 对外流量策略 |
|---|---|---|---|---|
| Phase 0 | 基线冻结与全量盘点 | 冻结旧语义、补齐观测和数据清单 | 事实清单、字段映射、功能矩阵、快照备份、统一追踪 ID | 不切流量 |
| Phase 1 | 基础设施落地 | 新运行底座 ready | PostgreSQL / Redis / MinIO / Temporal / API v2 骨架 | 不切流量 |
| Phase 2 | 新数据主模型落地 | 建主事实库与对象制品层 | 新 schema、artifact registry、迁移框架 | 不切流量 |
| Phase 3 | Seed / Graph 后端重建 | 上传、seed、graph 迁入新架构 | ingest workflow、seed projections、graph workflow、graph query | 不切流量，只做新栈构建与影子校验 |
| Phase 4 | Archive / Worldline / Writer 后端重建 | 建 canon 真源、worldline、draft durable state | archive 聚合、memory timeline、chapter context、worldline、draft workflow | 不切流量，只做新栈构建与影子校验 |
| Phase 5 | 前端重建、迁移演练与正式切换 | React 工作台完成并执行 cutover | 新前端、迁移 rehearsal、故障演练、回滚演练、正式切换 | 仅在最终闸门通过后一次切换 |

建议节奏按 12 到 16 周组织，但真正的推进单位不是“周”，而是“阶段出口条件是否满足”。

## 2.1 并行执行总规则

本轮允许使用 subagent 并行，但并行必须服从以下顺序：

1. Phase 0-2 以基线冻结和底座建设为主，只允许有限并行。
2. 进入业务重建后，后端按 `project/seed/graph`、`archive/llm`、`worldline/writer` 分批并行。
3. 前端并行必须晚于 contracts 与对应后端 query/command 稳定。
4. `writer` 不能早于 `worldline + archive + llm-facility`。
5. `worldline` 不能早于 `graph + archive`。

具体 lane 与写边界以 `12-Subagent-并行执行协议.md` 为准。

  - `seed_job_status_view`
  - `artifact_catalog_view`
- 兼容旧接口：
  - `POST /api/project/seed/extract`
  - `GET /api/project/task/<task_id>`

### 切换方式

## Phase 4：Archive / Memory / Chapter Context 迁移

### 里程碑目标

- 建立统一的档案、记忆和章节上下文查询面，消灭“JSON 真源 + SQLite 索引”的分裂模式。

- 将 `candidate / canon / experiment` 和记忆事件时间线正式入库。
- 建立 `ChapterContextQueryService`，直接读取新 projection，不再跨 JSON 和运行时 SQLite 拼装。
- 兼容旧接口：
  - `GET /api/archive/library`
  - `GET /api/archive/library/<archive_id>`
  - `GET /api/archive/library/<archive_id>/memory`
  - `GET /api/archive/library/<archive_id>/memory/timeline`
  - `POST /api/archive/library/<archive_id>/memory/<memory_id>/adopt`
  - `POST /api/novel/chapter-context`

### 切换方式

- 先以旧 `narrative_archives.json` 和 `archive_library.sqlite3` 为输入做回填。
- 新档案审核写路径启用双写：旧 SQLite 与新 PostgreSQL 同时更新。
- 前端的 chapter context 查询先做影子对比，再切到新查询面。

### 出口条件

- 对同一 `archive_id`，旧 timeline 与新 timeline 的事件序列一致。
- `chapter context` 的 `must_know / warnings / scene_candidates` 主要内容对齐。
- 新的 archive/memory 查询不再依赖项目目录 JSON。
- `archive-library` 页面与 memory review 所有功能已在新前端可用。

### 回滚条件

- 若新 timeline 或 context pack 出现明显语义漂移，前端查询立即切回旧接口实现。
- 双写期间以旧 SQLite/JSON 为 canon 真源；新库标记为 shadow data，不进入 writer/worldline。

## 4. 三个最大技术风险与绝对安全回滚预案

## 风险 1：数据迁移导致 canon 事实错乱或丢失

### 风险描述

当前系统的数据真源分散在项目目录 JSON、多个 SQLite、运行时文件和派生索引中。最危险的不是“迁不过去”，而是“迁过去了但 canon/candidate、chapter history、worldline event 顺序错了”，这种错误很难第一时间发现。

### 触发信号

- 同一项目在新旧系统中的 archive 数、memory event 数、timeline event 数对不上。
- `chapter context` 的必知条目、记忆 timeline、worldline latest event 出现明显偏差。
- 任一迁移批次 checksum 不一致。

### 绝对安全回滚预案

1. 切换前对 `backend/uploads/` 和所有旧 SQLite 做不可变快照。
2. 新库迁移全部采用“追加写入 + 校验通过后打 `active` 标记”，不覆盖旧数据。
3. 切读之前，旧系统保持唯一 canon 真源地位。
4. 一旦发现偏差：
   - 立即关闭新库读流量；
   - 停止双写；
   - 将新库当批次数据统一标记为 `rollback_discarded`；
   - 查询全面切回旧 JSON/SQLite；
   - 使用快照重新演练该批次迁移。

### 回滚边界

- 回滚只影响新库和兼容层，不允许删除旧项目目录中的任何文件。

---

## 风险 2：Workflow 重写后长流程堆积、卡死或不可恢复

### 风险描述

seed、worldline prepare、auto-evolve、draft 都会频繁调用 LLM。若 workflow/activity 设计不当，会出现 worker 堵塞、重试风暴、SSE 长连接无终态、数据库写放大等问题。

### 触发信号

- Temporal queue backlog 持续增长。
- 同类 operation 的平均耗时和 P95 急剧上升。
- 同一 operation 重试次数异常增加。
- 前端看到“运行中”但服务端没有步骤推进。

### 绝对安全回滚预案

1. 新 workflow 上线时必须与旧执行路径并存，且入口受 feature flag 控制。
2. API 兼容层保留“旧执行器”开关，不把新 workflow 作为唯一实现。
3. 任一 workflow 出现堆积或不可恢复时：
   - 立即关闭对应 feature flag；
   - 停止创建新的 v2 operations；
   - 入口流量回切至旧 Flask 任务路径；
   - 已经运行中的 v2 operation 标记为 `terminated_by_rollback`；
   - 旧路径重新成为唯一执行路径。

### 回滚边界

- 回滚只影响“新创建的 operation”；旧系统业务照常。

---

## 风险 3：接口契约切换导致前端工作台失效或状态错配

### 风险描述

当前前端直接依赖旧 Flask 接口和 SSE 事件格式。若新后端在切换时同时改 URL、字段名、分页、错误结构和 SSE 事件语义，`/writer` 和 `/worldline` 会第一时间失效。

### 触发信号

- 新前端页面能打开，但关键操作无响应或状态错乱。
- 旧前端调用兼容层后出现字段缺失、SSE 事件无法解析、轮询结果与操作状态不一致。
- `draft generate`、`worldline prepare`、`chapter context` 三条主链任一断裂。

### 绝对安全回滚预案

1. 在整个迁移期保留兼容 API / BFF 层，旧前端不直接连新应用服务。
2. v2 契约先对接新前端，旧 URL 由兼容层转换，不要求旧前端同步改版。
3. 一旦出现联调故障：
   - 网关或 BFF 路由立即切回旧 handler；
   - 新前端路由降级到旧工作台入口；
   - 所有旧接口继续保持可用；
   - 对 v2 契约问题单独修复，不影响线上主链。

### 回滚边界

- 回滚是路由层和契约层切换，不是数据库层回滚。

## 5. 最终切换闸门

只有同时满足以下条件，才允许宣布旧系统退役：

1. Seed、archive/memory、worldline、draft 四条主链已全部在新架构下独立可运行。
2. `06-09` 四份补充文档中不存在未关闭的 `TBD / unknown / not planned` 项。
3. 新系统连续一段稳定窗口内无高优先级数据不一致。
4. 旧接口只剩兼容层，不再直接触达旧业务逻辑。
5. 新前端已经覆盖全部 8 个旧路由页面及其关键子功能。
6. 已完成一次完整的“故障注入 -> 回滚 -> 再恢复”演练。

在此之前，任何“删除旧 JSON 文件写路径”“删除旧 SQLite 读取逻辑”“删除旧 Vue 工作台”的动作都不允许发生。
