# 01-架构与技术栈落地

## 1. 文档目标与适用范围

本文档只回答一件事：基于当前 `MiroFish-Novel` 仓库的真实结构，如何把现有系统从“Flask + Vue + SQLite/文件系统 + 线程任务”的工作流脚本式单体，重构为“DDD 模块化单体 + Hexagonal + CQRS + Durable Workflow”的目标架构，并明确前后端技术栈、目录结构、依赖管理、开发规范和部署规范。

本文档严格立足当前仓库现状，关键事实如下：

- 后端当前是 `Flask` 单应用，统一注册 `project / novel / worldline / llm / archive` 蓝图。
- 前端当前是 `Vue 3 + Vite`，以多个工作台页面直接承载复杂业务编排。
- 长任务当前由 API 直接拉起 `threading.Thread` 执行。
- 持久化当前混用项目目录 JSON、多个本地 SQLite、文本文件与运行时文件夹。
- `writer` 与 `worldline` 已经是产品价值中心。
- LLM 调用已经具备“设施面板 + 模块绑定”的基础设施雏形，这部分不应推倒重做，而应升级为正式的基础设施能力。

## 2. 当前仓库现状总览

### 2.1 后端现状

当前后端核心结构：

- `backend/app/api/`: Flask 蓝图层，按 `project / novel / worldline / llm / archive` 划分。
- `backend/app/services/`: 绝大多数业务逻辑放在这里，包含 seed、archive、worldline、draft_agents、llm 等服务。
- `backend/app/models/`: 不是严格 ORM 层，更多是文件模型和任务模型。
- `backend/app/utils/`: 文件解析、日志、LLM client 等基础工具。
- `backend/tests/`: 已有大量 pytest 覆盖，说明仓库不是原型，而是已有可验证主链。

当前运行模型：

- `backend/run.py` 直接 `app.run(threaded=True)`。
- `seed_extract_task_service.py` 通过本地线程执行长流程。
- `worldline`、`writer`、`archive memory review`、`llm facility` 都在同一个进程边界里。

### 2.2 前端现状

当前前端核心结构：

- `frontend/src/views/`: 直接挂工作台视图，如 `/writer`、`/worldline`、`/character-console`、`/llm-facility`。
- `frontend/src/api/`: 手写 `fetch` 请求层和 SSE 封装。
- `frontend/src/composables/`: 少量状态组合逻辑。
- `frontend/src/router/index.js`: 直接路由到各工作台。

当前前端特征：

- 无统一 server-state 管理层。
- 无类型化 API client。
- 页面组件承担了大量“请求编排 + 业务状态 + UI 渲染”三重职责。
- 工作台已经复杂到需要多列布局、SSE、任务轮询、长链路进度展示。

### 2.3 当前持久化现状

当前数据不在一个统一事实源中，而是拆散在多个介质里：

- 项目元数据：`backend/uploads/projects/<project_id>/project.json`
- 上传原文：`backend/uploads/projects/<project_id>/files/*`
- 提取文本与中间产物：项目目录下 `.txt/.json`
- 任务运行态：`task_runtime.sqlite3`
- LLM 配置：`llm_facility.sqlite3`
- 档案库：`archive_library.sqlite3`
- worldline session：项目目录或全局目录下 `session.json`
- worldline runtime：独立 SQLite

这意味着当前系统没有单一主存，没有统一事务边界，也没有标准化 projection 层。

### 2.4 当前真正有价值的部分

当前仓库并非一无是处，以下部分是值得保留和升级的：

- 领域命名已经基本正确：`project / archive / writer / worldline / llm`
- LLM 设施面板已经形成“模块绑定”思路
- `writer`、`worldline`、`memory review` 已有清晰产品语义
- 后端已有大量用例测试，说明领域行为可被回归验证

## 3. 新老架构差异点

本节按“当前仓库现状 vs 目标架构”逐项对照。

### 3.1 总体架构

| 维度 | 当前仓库现状 | 目标架构 |
|---|---|---|
| 架构形态 | 工作流脚本式单体 | DDD 模块化单体 |
| 业务边界 | 通过 `services/` 命名弱分层 | 按 `domain / application / infrastructure / interface` 明确边界 |
| 依赖方向 | API -> service，service 之间横向互调较多 | Interface -> Application -> Domain，Infrastructure 通过 Port 注入 |
| 长流程执行 | API 内线程、同步拼装、进程内状态 | Durable Workflow 引擎负责编排，API 只发命令和订阅状态 |
| 查询模型 | 服务层跨文件/跨 SQLite 读取 | CQRS：命令模型与查询投影分离 |
| 存储策略 | JSON + SQLite + 文件系统并存 | PostgreSQL 为主事实库，Redis 为瞬时状态，MinIO 为大对象存储 |

### 3.2 后端分层

| 维度 | 当前仓库现状 | 目标架构 |
|---|---|---|
| Web 框架 | Flask 蓝图 | FastAPI 路由 + Pydantic DTO |
| 服务层 | 一个 `services/` 包承载全部业务 | 每个 bounded context 有独立 application service |
| 模型层 | 文件模型 + dataclass + 手写 SQLite | SQLAlchemy 2 + 聚合根 + Repository Port |
| 领域事件 | 基本没有显式事件模型 | 所有关键状态变更显式为领域事件 |
| 工作流编排 | service 内串行调 agent/service | Temporal workflow/activity 编排 |
| 依赖注入 | 多数 service 内部直接实例化依赖 | 通过 composition root 注入 port/adapters |

### 3.3 前端分层

| 维度 | 当前仓库现状 | 目标架构 |
|---|---|---|
| 核心框架 | Vue 3 + Vite | React + TypeScript + Vite |
| 页面组织 | `views` 直挂大型工作台组件 | `routes + features + entities + shared` 模块化前端 |
| Server State | 手写 fetch + 局部 ref/composable | TanStack Query |
| Client State | 组件内状态、散落的 composable | Zustand 按业务切 store |
| API 契约 | 手写 JS 请求函数 | OpenAPI 生成类型化 client + shared contracts |
| 实时链路 | 手写 SSE 工具 | 统一 event stream client + 领域订阅协议 |

### 3.4 数据与持久化

| 维度 | 当前仓库现状 | 目标架构 |
|---|---|---|
| 主数据源 | 无 | PostgreSQL |
| 原始文本/生成正文/制品 | 文件系统项目目录 | MinIO 对象存储 |
| 运行态缓存 | 基本没有统一缓存层 | Redis |
| 任务状态 | SQLite 表 + JSON 结果 | Workflow state + read models |
| worldline 状态 | session JSON + runtime SQLite | 事件流 + PostgreSQL projection |
| 档案库 | 独立 SQLite | Archive bounded context 下标准表结构 |

### 3.5 工作流与实时执行

| 维度 | 当前仓库现状 | 目标架构 |
|---|---|---|
| Seed 提取 | `threading.Thread` + TaskManager | `IngestWorkflow / SeedAnalysisWorkflow` |
| Writer 正文生成 | SSE 接口直接驱动 orchestrator | `DraftWorkflow` 异步执行，SSE 只订阅状态 |
| Worldline 自动演化 | API/service 直接推进 | `WorldlineEvolutionWorkflow` |
| 失败语义 | 局部存在 silent fallback | 显式失败、可重试、可补偿、可终止 |
| 可恢复性 | 进程级脆弱 | Worker 崩溃后可恢复 |

### 3.6 部署与运行环境

| 维度 | 当前仓库现状 | 目标架构 |
|---|---|---|
| 部署方式 | 本地手工起前后端 | Docker Compose 为标准开发/单机场景 |
| 服务拆分 | 前端 + 后端 | web / api / workflow-worker / postgres / redis / minio / temporal / temporal-ui |
| 配置管理 | `.env` + 代码默认值 | 分环境 `.env` + secrets + typed settings |
| 观测能力 | 基础日志 | 结构化日志 + trace id + workflow 可观测面板 |

### 3.7 测试体系

| 维度 | 当前仓库现状 | 目标架构 |
|---|---|---|
| 后端测试 | pytest 覆盖较多 | pytest + contract tests + workflow tests + migration tests |
| 前端测试 | 构建验证为主，少量局部测试 | Vitest + React Testing Library + Playwright |
| API 兼容验证 | 手工为主 | OpenAPI contract test + backward compatibility suite |
| 数据迁移验证 | 局部 SQLite migration test | 全链路 migration rehearsal + checksum 校验 |

## 4. 目标架构主轴

目标架构不是微服务，而是一个强约束的、可持续演进的模块化单体。

### 4.1 架构原则

1. 单一业务系统，单一事实主库
   小说工作空间下的 project、archive、worldline、draft 高度耦合，优先保证统一事实源，而不是强行拆服务。

2. 领域边界显式化
   至少拆成以下 bounded contexts：
   - `identity-and-project`
   - `archive-library`
   - `seed-analysis`
   - `worldline`
   - `writer`
   - `llm-facility`
   - `workflow-orchestration`

3. Application 层只编排，不承载基础设施细节
   Application service 只负责命令处理、事务边界、事件发布，不直接写 SQL、文件或调用第三方 SDK。

4. Domain 层不依赖框架
   领域对象、聚合根、值对象、领域服务不直接依赖 FastAPI、SQLAlchemy、Redis、Temporal SDK。

5. Workflow 与 API 分离
   API 的职责是接收命令、查询投影、推送事件；真正的长流程由 workflow worker 执行。

### 4.2 建议的 bounded contexts

#### A. `project`

负责：

- 小说工作空间创建
- 原稿上传
- 项目元数据
- 项目级配置

不负责：

- seed 具体分析逻辑
- draft 生成
- worldline 演进

#### B. `seed-analysis`

负责：

- 文本切分
- 提取 block facts
- ontology 生成
- 角色/组织/关系候选输出
- seed artifacts 产出

#### C. `archive-library`

负责：

- 档案聚合
- memory layer（canon / candidate / experiment）
- 记忆审核与晋升
- 时间线追踪

#### D. `worldline`

负责：

- 单世界 session
- 变量注入
- 推演步骤
- agent roster
- 事件采纳与拒绝
- runtime memory 投影

#### E. `writer`

负责：

- chapter context pack
- style / memory / context / reviewer / writer 各 agent 的应用编排
- draft 生成、审校、修订

#### F. `llm-facility`

负责：

- channel
- module binding
- model sync
- concurrency policy
- request audit metadata

#### G. `workflow-orchestration`

负责：

- seed analysis workflow
- worldline evolution workflow
- draft workflow
- repair / retry / compensation policy

### 5.1 目录设计解释

#### `apps/web`

对应当前 `frontend/`，但不再把页面写成超大工作台组件。
每个工作台由：

- `pages/` 承接路由级容器
- `features/` 承接业务功能块
- `entities/` 承接通用领域 UI 与视图模型
- `shared/` 承接设计系统、请求基建、hooks、工具函数

#### `apps/api`

对应当前 `backend/`，但后端代码必须按模块内聚，不再把几乎所有业务塞进一个 `services/` 包。

#### `workflows`

这是当前仓库完全缺失但必须补齐的层。
所有长链路：

- 上传后分析
- worldline 自动演化
- 正文生成
- 修订

都应由 workflow worker 承担。

#### `packages/contracts`

这是前后端真正共享的契约层。
它的作用是：

- 统一 OpenAPI 规范
- 生成 TypeScript client/types
- 为 API contract tests 提供稳定 schema

#### `infra`

把 Docker、Compose、Temporal、MinIO、Postgres 初始化脚本和环境脚本统一收口。
当前仓库缺少这一层，因此环境复现不标准。

#### `migrations`

旧系统现在存在大量 SQLite/JSON/文件系统产物。
这些迁移逻辑不能散落在脚本角落，必须成为一级目录，含 rehearsal 和 runbook。

## 6. 新老技术栈替换对应表

本表只列与当前项目高度相关的关键替换项。

| 类别 | 当前技术栈 | 目标技术栈 | 替换理由 |
|---|---|---|---|
| 前端框架 | Vue 3 + JS + Vite | React 19 + TypeScript + Vite | 当前前端已是复杂工作台，React 生态在复杂 server-state、类型化 API 和专业工作台拆分上更稳 |
| 状态管理 | 组件状态 + composables | TanStack Query + Zustand | 区分 server state 与 client state，避免工作台组件继续膨胀 |
| API 层 | 手写 `fetch` 封装 | OpenAPI + openapi-typescript/orval 生成 client | 避免前后端契约漂移，减少手写 DTO 和字段错误 |
| UI 组件 | 自写样式组件 | Tailwind CSS + Radix UI + shadcn/ui | 提供可控、可组合、无强设计绑架的工作台基建 |
| 表单/校验 | 手写校验 | React Hook Form + Zod | 配合复杂命令表单、typed schema 和可维护性 |
| 路由 | vue-router | React Router | 与 React 生态协同，无额外心智成本 |
| SSE/实时 | 手写 SSE helper | 统一 stream client + Query invalidation 策略 | 让长流程更新和查询刷新具备固定模式 |
| 后端语言 | Python 3.11 | Python 3.12 | 保持 Python/LLM 生态优势，同时升级运行时能力 |
| 后端框架 | Flask | FastAPI | 原生 async 支持、OpenAPI 自动产出、Pydantic 集成更适合契约化 API |
| 数据建模 | 手写 dataclass/JSON/SQLite | SQLAlchemy 2 + Alembic | 统一数据建模、迁移和事务边界 |
| 工作流引擎 | 本地线程 + service 串行调用 | Temporal | Durable workflow、重试、恢复、可观测性都是当前长链路所需 |
| 数据库 | 多个本地 SQLite + JSON | PostgreSQL | 提供统一主事实库、事务、索引、JSONB、复杂查询能力 |
| 缓存/短态 | 无统一缓存 | Redis | 用于瞬态查询缓存、分布式锁、订阅 fanout、节流 |
| 对象存储 | 本地文件系统 | MinIO | 统一存原稿、大文本、中间制品、生成结果，便于迁移与备份 |
| LLM 接入 | 自定义 OpenAI-compatible client | 保留并升级为 adapter 层 | 当前设施面板是可保留资产，但要从 util 提升为正式基础设施模块 |
| 部署方式 | 手工本地起服务 | Docker Compose 单机标准化部署 | 当前项目明确适合单机多容器，不需要先拆微服务 |
| 测试体系 | pytest + 构建验证 | pytest + mypy + ruff + Vitest + RTL + Playwright + contract tests | 当前系统是工作流产品，必须补齐契约与前端行为测试 |
| 配置管理 | `.env` + 代码默认值 | Pydantic Settings + `.env.example` + Compose env injection | 避免环境配置漂移，便于本地/测试/部署复现 |

## 7. 开发环境搭建与依赖管理规范

本节定义目标项目的工程规范，而不是对当前仓库的运行方式做描述。

### 7.1 包管理与版本管理原则

#### 前端

- 统一使用 `pnpm`
- 根目录使用 `pnpm-workspace.yaml`
- 所有前端依赖固定大版本
- 严禁在 `apps/web` 之外随意安装前端依赖

#### Python

- 统一使用 `uv` 管理虚拟环境与依赖锁定
- `apps/api` 和 `workflows` 分别维护 `pyproject.toml`
- 锁文件必须提交到仓库
- 本地不允许“直接 pip install 某个包但不入锁文件”

#### 版本管理

- Node 版本固定，例如 `20.x`
- Python 版本固定，例如 `3.12.x`
- 在仓库根放置 `.tool-versions` 或 `mise.toml`
- CI、Docker、本地版本必须一致

### 7.2 本地开发规范

2. 半本地方式

### 7.7 工作流开发规范

#### Workflow 设计原则

- workflow 只负责编排，不写业务细节
- activity 才调用数据库、对象存储、LLM adapter
- 每个 workflow 都必须定义：
  - 输入契约
  - 输出契约
  - retry policy
  - timeout policy
  - cancellation policy
  - event stream schema

#### 当前项目中必须 workflow 化的链路

1. 原稿上传后的 seed analysis 全链路
2. worldline 自动演化
3. draft generate
4. draft revise
5. 大规模 archive sync / repair

### 7.8 依赖管理红线

以下行为必须禁止：

- 在前端直接手写与 OpenAPI 不一致的接口字段
- 在 domain 层 import FastAPI/SQLAlchemy/Temporal SDK
- 在 API 层直接写复杂业务编排
- 在 workflow 中塞入大文本 payload
- 把原稿、正文全文或大 JSON 塞进 Redis
- 新增 SQLite 作为“临时过渡主存”
- 为了运行成功加入 silent fallback 或 mock success

## 9. 本文档的 5 个落地结论

1. 目标不是微服务，而是强边界的 DDD 模块化单体。
   当前项目核心问题是领域边界和工作流持久化缺失，不是“服务拆得不够多”。

2. 必须引入 Durable Workflow。
   `seed / worldline / draft` 都是长流程 LLM 编排，不适合继续靠 API 线程和进程内状态支撑。

3. 必须统一到 PostgreSQL + Redis + MinIO。
   当前 JSON/SQLite/文件系统碎片化存储是结构性上限。

4. 前端必须转为 React + TypeScript + Query/Store 分层。
   当前工作台复杂度已经超过“组件里写请求逻辑”的舒适边界。

5. LLM 设施面板应保留，但必须升级为正式基础设施模块。
   它是当前少数值得继续投资的架构资产。

## 10. 推荐执行顺序

本文件不展开迁移计划细节，但从技术栈与架构落地角度，建议顺序应是：

1. 先搭目标工程骨架与基础设施
2. 再建立 PostgreSQL schema、OpenAPI 契约和 contracts 生成链
3. 再把 workflow worker 跑起来
4. 再迁移 `project / archive / worldline / writer`
5. 最后切前端工作台

如果顺序反过来，例如先重写页面或先拆接口，会把当前仓库已经存在的边界问题继续复制到新架构里。
