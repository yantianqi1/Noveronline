# 02. 数据模型与持久化迁移方案

## 0. 文档结论先行

当前仓库的持久化层不是一个统一的数据系统，而是“项目目录 JSON + 多个职能型 SQLite + 少量索引文件”的拼装体。它能支撑离线开发，但不适合作为长期演进的生产级事实源。

最关键的问题不是 SQLite 本身，而是：

- 事实源分裂：同一业务事实同时散落在 `project.json`、项目产物 JSON、全局 SQLite、worldline runtime SQLite、prepare SQLite 中。
- 真源与索引混淆：例如 `archive_library.sqlite3` 实际上是从 `narrative_archives.json` 增量同步出来的索引库，不应承担主事实库职责。
- 结构化实体和大文本产物混存：章节正文、分析产物、状态快照、配置、事件日志都被当作同一层级数据处理。
- 单世界语义没有在存储层收口：`branch_id`、`branch_count`、`source_branch_id` 仍残留在多处表和 JSON 中。
- 工作流没有 durable state machine：`task_runtime.sqlite3` 只能记任务壳，不能表达可恢复步骤、幂等重试、输入输出引用和回放。

目标架构下，必须把持久化重建为四层：

1. `PostgreSQL` 作为唯一主事实库。
2. `对象存储` 作为原文、长文本、JSON 制品和大体积生成物的归档层。
3. `Redis` 只承担缓存、锁、SSE fanout、并发控制，不保存 canon 事实。
4. `Projection / Read Model` 作为查询模型，落 PostgreSQL 专用表或物化视图。

## 1. 旧系统真实持久化层盘点与痛点

以下内容基于当前仓库真实代码与现有落盘路径，不是推测。

### 1.1 项目目录 + JSON 事实源

当前实现位置：

- `backend/app/models/project.py`
- `backend/app/services/seed_extract_runner.py`
- 实际目录：`backend/uploads/projects/<project_id>/`

当前行为：

- `project.json` 保存项目元数据。
- `files/` 保存原始上传文件。
- `extracted_text.txt` 保存提取后的全文。
- `chapter_segments.json`、`analysis_blocks.json`、`anchor_points.json`、`story_memory.json`、`story_memory_snapshots.json`、`block_analyses.json`、`chapter_cards.json`、`chapter_continuity.json`、`consistency_report.json`、`seed_analysis.json` 等中间产物直接写项目目录。
- `draft/finalize` 还会直接回写 `chapter_segments.json`、`chapter_cards.json`、`chapter_continuity.json`。

技术痛点：

- 项目元数据、原文、结构化产物和工作流阶段结果混在同一命名空间，没有生命周期分层。
- JSON 文件被多个服务直接读写，没有事务边界，也没有版本一致性控制。
- 回写行为是覆盖式写入，不具备事件溯源、审计和冲突检测能力。
- 大量“结构化数据”其实已经是数据库对象，却被保存在文件里，导致查询、聚合、增量同步都很差。
- 文件名语义即 schema，极易漂移，没有迁移框架。

### 1.2 `task_runtime.sqlite3`

当前实现位置：

- `backend/app/models/task.py`
- `backend/app/models/task_storage.py`
- 实际路径：`backend/uploads/system/task_runtime.sqlite3`

当前表：

- `task_runs`

技术痛点：

- 只有任务壳，没有步骤级执行记录，无法表达 `extract -> segment -> analyze -> archive -> graph` 的真实状态。
- `result_json`、`metadata_json`、`progress_detail_json` 都是 blob 字段，无法建立稳定查询模型。
- 任务由 Flask 进程内线程触发，SQLite 只是在补写状态，不是 workflow engine。
- 进程级单例 + 本地 SQLite 让扩容、恢复、幂等重试都不可靠。

### 1.3 `llm_facility.sqlite3`

当前实现位置：

- `backend/app/services/llm_storage.py`
- `backend/app/services/llm_settings_service.py`
- 实际路径：`backend/uploads/system/llm_facility.sqlite3`

当前表：

- `llm_channels`
- `llm_models`
- `llm_module_bindings`

技术痛点：

- `api_key` 明文保存在 SQLite。
- `llm_models` 是上游模型列表缓存，不是稳定事实，却和配置混存。
- 缺少 provider / channel / model capability / module policy 的分层。
- 不支持密钥轮换、版本化绑定、审计。

### 1.4 `archive_library.sqlite3`

当前实现位置：

- `backend/app/services/archive_library_storage.py`
- `backend/app/services/archive_library_service.py`
- 实际路径：`backend/uploads/system/archive_library.sqlite3`

当前表：

- `archive_library`
- `archive_sources`
- `archive_agent_memory`
- `archive_agent_memory_events`

技术痛点：

- `archive_library` 不是原生主库，而是从每个项目的 `narrative_archives.json` 增量同步出来的全局索引库。
- 档案正文和长期记忆都挂在同一个 SQLite 中，写路径和同步路径耦合。
- `archive_sources` 只是文件索引元数据，不是业务事实。
- 记忆模型虽然已经比别处进步，但依然混入了 `source_branch_id` 等旧世界观遗留字段。

### 1.5 `chapter_meta.sqlite3`

当前实现位置：

- `backend/app/services/chapter_meta_storage.py`
- `backend/app/services/chapter_meta_service.py`
- 实际路径：`backend/uploads/system/chapter_meta.sqlite3`

当前表：

- `chapter_meta`
- `chapter_history_item`

技术痛点：

- 这是从 `chapter_cards.json` 派生出来的检索库，但当前又被当作事实源消费。
- 现有 schema 明显存在历史漂移：实际库里仍保留 `chapter_index`，服务层已转向 `chapter_order`。
- `chapter_history_item` 混装世界规则、线程、事件、角色状态、关系变化，没有统一主键和来源模型。
- 最终章节正文不在这张库里，导致“章节正文”和“章节卡/历史项”脱节。

### 1.6 worldline runtime / prepare SQLite

当前实现位置：

- `backend/app/services/worldline_runtime_storage.py`
- `backend/app/services/worldline_prepare_storage.py`
- `backend/app/services/world_state_store.py`
- 典型路径：
  - `backend/uploads/projects/<project_id>/worldlines/runtime.sqlite3`
  - `backend/uploads/projects/<project_id>/worldlines/prepare.sqlite3`
  - `backend/uploads/projects/<project_id>/worldlines/sessions/<session_id>/session.json`

当前事实分布：

- `session.json` 保存 worldline session 和 timeline。
- `index.json` 保存 session 索引。
- `prepare.sqlite3` 保存 prepare run、agent dossier、prepare event log。
- `runtime.sqlite3` 保存 agent registry、state snapshots、actions、dialogues、relations、episodic memory。

技术痛点：

- session 元数据在 JSON，agent runtime 在 SQLite，prepare 在另一套 SQLite，世界线事实被分成三块。
- 单世界模型下依然普遍存在 `branch_id` 作为一等字段，说明领域模型未真正收口。
- `agent_registry`、`agent_state_snapshots`、`relation_state_log` 都是快照式结构，缺少明确事件边界。
- 会话目录与项目目录耦合，跨项目或全局会话需要特殊路径分支。

### 1.7 `story_graph.json` + `story_graph.sqlite3`

当前实现位置：

- `backend/app/services/local_story_graph_storage.py`
- 理论落点：
  - `backend/uploads/projects/<project_id>/story_graph.json`
  - `backend/uploads/projects/<project_id>/story_graph.sqlite3`

当前行为：

- `story_graph.json` 保存完整图谱快照。
- `story_graph.sqlite3` 是同一份图谱的查询索引。

技术痛点：

- 同一图谱维护双份存储，JSON 是真源、SQLite 是检索索引，但两者缺少独立版本号和校验关系。
- 图节点、边、证据已经非常接近关系型模型，却仍靠整个快照重建索引。
- 图谱不能自然接入 archive、memory、worldline 的统一事实层。

### 1.8 额外但必须提到的隐含数据源

虽然题目只强制要求上述几类，但实际迁移必须同时考虑这些同目录 JSON：

- `narrative_archives.json`
- `story_memory.json`
- `story_memory_snapshots.json`
- `seed_analysis.json`
- `chapter_cards.json`
- `chapter_continuity.json`
- `reviewer_rules.json`

原因很简单：当前 SQLite 并没有覆盖这些业务对象，而新系统不能假装它们不存在。

## 2. 目标持久化架构总览

### 2.1 存储分层

#### PostgreSQL：唯一主事实库

保存：

- `workspace / project`
- `manuscript / file metadata / artifact metadata`
- `workflow run / workflow step`
- `canonical entity / archive`
- `memory / memory_event`
- `worldline session / current world / timeline event / agent state / action / dialogue`
- `draft workflow / draft / review / finalized chapter`
- `llm provider / channel / module binding`
- 所有 projection/read model 表

不保存：

- 原始大文件二进制
- 超长生成正文原文 blob
- 大型 JSON 制品正文

#### Redis：严格限定为易失层

保存：

- workflow dispatch queue 元数据或 worker lease
- channel 并发信号量
- SSE / WebSocket fanout 缓冲
- 热点 projection cache
- 短 TTL 去重键、幂等键、锁

绝不保存：

- canon 事实
- 唯一可恢复的 workflow state
- 长期记忆或最终章节正文

#### 对象存储：长文本与制品归档层

保存：

- 原始上传文件
- `extracted_text.txt`
- 章节切分、锚点、分析块、上下文包、story memory、graph snapshot 等 JSON 制品
- draft 正文、review report、writer context pack、大段日志

规则：

- PostgreSQL 只保存对象元数据和引用，不保存长文本正文。
- 每个对象必须有 `storage_key + sha256 + byte_size + content_type + semantic_type`。

#### Projection / Read Model：查询模型

实现方式：

- PostgreSQL 专用 projection 表
- 必要时使用物化视图

典型 read model：

- 项目总览
- archive library 搜索
- writer 上下文预览
- worldline 当前世界摘要
- timeline feed
- LLM 设施面板快照

## 3. 目标数据模型与 Schema 设计

以下设计按领域拆分，字段采用偏 PostgreSQL 的表达方式。

### 3.1 Workspace / Project

#### `workspaces`

```sql
create table workspaces (
  workspace_id uuid primary key,
  workspace_key text not null unique,
  name text not null,
  owner_user_id uuid,
  status text not null default 'active',
  created_at timestamptz not null,
  updated_at timestamptz not null
);
```

#### `projects`

```sql
create table projects (
  project_id uuid primary key,
  workspace_id uuid not null references workspaces(workspace_id),
  project_key text not null unique,
  name text not null,
  project_type text not null default 'novel',
  status text not null,
  analysis_goal text not null default '',
  active_ingest_run_id uuid,
  active_worldline_session_id uuid,
  active_draft_run_id uuid,
  latest_graph_artifact_id uuid,
  latest_seed_artifact_id uuid,
  latest_archive_snapshot_id uuid,
  error_code text,
  error_message text,
  created_at timestamptz not null,
  updated_at timestamptz not null
);
```

设计原则：

- `project.json` 的职责全部收束到 `projects`。
- 当前“项目状态”不再通过覆盖 JSON 更新，而是可被 workflow 和 projection 推导。

### 3.2 Manuscript / File / Artifact

#### `manuscripts`

```sql
create table manuscripts (
  manuscript_id uuid primary key,
  project_id uuid not null references projects(project_id),
  source_filename text not null,
  media_type text not null,
  file_extension text not null,
  storage_key text not null unique,
  sha256 text not null,
  byte_size bigint not null,
  upload_status text not null,
  uploaded_at timestamptz not null
);
```

#### `artifacts`

```sql
create table artifacts (
  artifact_id uuid primary key,
  project_id uuid references projects(project_id),
  workflow_run_id uuid,
  workflow_step_id uuid,
  artifact_type text not null,
  semantic_scope text not null,
  storage_backend text not null,
  storage_key text not null unique,
  content_type text not null,
  sha256 text not null,
  byte_size bigint not null,
  schema_version integer not null,
  metadata_jsonb jsonb not null default '{}'::jsonb,
  created_at timestamptz not null
);
create index idx_artifacts_project_type on artifacts(project_id, artifact_type, created_at desc);
```

说明：

- 当前目录里的 `chapter_segments.json`、`story_memory.json`、`seed_analysis.json`、`reviewer_rules.json`、draft 输出正文、review report 都统一进 `artifacts`。
- 对象存储是真正载体，`artifacts` 只是索引和引用。

### 3.3 Ingest Workflow

#### `workflow_runs`

```sql
create table workflow_runs (
  workflow_run_id uuid primary key,
  project_id uuid references projects(project_id),
  workflow_type text not null,
  workflow_engine text not null,
  external_run_key text,
  status text not null,
  trigger_source text not null,
  requested_by text not null default 'system',
  input_jsonb jsonb not null default '{}'::jsonb,
  output_jsonb jsonb not null default '{}'::jsonb,
  started_at timestamptz,
  finished_at timestamptz,
  error_code text,
  error_message text,
  created_at timestamptz not null
);
create index idx_workflow_runs_project_type on workflow_runs(project_id, workflow_type, created_at desc);
```

#### `workflow_steps`

```sql
create table workflow_steps (
  workflow_step_id uuid primary key,
  workflow_run_id uuid not null references workflow_runs(workflow_run_id),
  step_key text not null,
  attempt_no integer not null,
  status text not null,
  started_at timestamptz,
  finished_at timestamptz,
  input_artifact_id uuid,
  output_artifact_id uuid,
  metrics_jsonb jsonb not null default '{}'::jsonb,
  error_jsonb jsonb not null default '{}'::jsonb,
  unique (workflow_run_id, step_key, attempt_no)
);
```

落地范围：

- ingest workflow
- worldline prepare workflow
- draft workflow

现有 `task_runtime.sqlite3` 仅作为迁移参考，不再保留。

### 3.4 Canonical Entity / Archive

#### `entities`

```sql
create table entities (
  entity_id uuid primary key,
  project_id uuid not null references projects(project_id),
  entity_uuid text,
  entity_kind text not null,
  canonical_name text not null,
  display_name text not null,
  summary text not null default '',
  attributes_jsonb jsonb not null default '{}'::jsonb,
  source_artifact_id uuid,
  source_version integer not null default 1,
  status text not null default 'active',
  created_at timestamptz not null,
  updated_at timestamptz not null
);
create index idx_entities_project_kind on entities(project_id, entity_kind, canonical_name);
```

#### `entity_aliases`

```sql
create table entity_aliases (
  entity_alias_id uuid primary key,
  entity_id uuid not null references entities(entity_id),
  alias text not null,
  unique (entity_id, alias)
);
```

#### `entity_relationships`

```sql
create table entity_relationships (
  relationship_id uuid primary key,
  project_id uuid not null references projects(project_id),
  relation_type text not null,
  source_entity_id uuid not null references entities(entity_id),
  target_entity_id uuid not null references entities(entity_id),
  summary text not null default '',
  weight integer not null default 0,
  attributes_jsonb jsonb not null default '{}'::jsonb,
  source_artifact_id uuid,
  created_at timestamptz not null,
  updated_at timestamptz not null
);
create index idx_entity_relationships_src on entity_relationships(source_entity_id);
create index idx_entity_relationships_tgt on entity_relationships(target_entity_id);
```

#### `archives`

```sql
create table archives (
  archive_id uuid primary key,
  project_id uuid not null references projects(project_id),
  entity_id uuid not null references entities(entity_id),
  archive_type text not null,
  agent_kind text not null,
  importance_tier text not null,
  selected_importance_tier text not null,
  template_key text not null,
  template_version text not null,
  can_act_as_agent boolean not null default true,
  payload_jsonb jsonb not null,
  source_artifact_id uuid,
  created_at timestamptz not null,
  updated_at timestamptz not null,
  unique (project_id, entity_id)
);
```

说明：

- `archive_library.sqlite3.archive_library` 不再是事实源。
- 真正的档案事实应来自 `archives`，全局检索只是 projection。

### 3.5 Memory / Memory Event

#### `memories`

```sql
create table memories (
  memory_id uuid primary key,
  project_id uuid not null references projects(project_id),
  archive_id uuid not null references archives(archive_id),
  memory_type text not null,
  memory_layer text not null,

  source_session_id uuid,
  source_timeline_event_id uuid,
  source_action_id uuid,
  source_dialogue_id uuid,
  source_artifact_id uuid,
  created_at timestamptz not null,
  updated_at timestamptz not null,
  adopted_at timestamptz,
  rejected_at timestamptz
);
create index idx_memories_archive_layer_status on memories(archive_id, memory_layer, status, updated_at desc);
create index idx_memories_archive_subject on memories(archive_id, normalized_subject, updated_at desc);
```

#### `memory_events`

```sql
create table memory_events (
  memory_event_id uuid primary key,
  memory_id uuid not null references memories(memory_id),
  archive_id uuid not null references archives(archive_id),
  event_type text not null,
  from_status text,
  to_status text,
  actor_type text not null,
  actor_ref text not null default '',
  evidence_jsonb jsonb not null default '[]'::jsonb,
  metadata_jsonb jsonb not null default '{}'::jsonb,

);
create index idx_memory_events_archive_created on memory_events(archive_id, created_at desc);
```

说明：

- `candidate / canon / experiment` 作为显式 enum 语义存在于 `memory_layer`。
- 当前 `archive_agent_memory_events` 的时间线能力应原样升级，而不是丢掉。

### 3.6 Worldline Session / Current World / Timeline / Agent State / Action / Dialogue

目标模型必须以“单世界”收口，不再把 `branch_id` 当核心事实字段。

#### `worldline_sessions`

```sql
create table worldline_sessions (
  session_id uuid primary key,
  project_id uuid references projects(project_id),

  source_archive_snapshot_id uuid,

  simulation_goal text not null,

  created_at timestamptz not null,
  updated_at timestamptz not null
);
```

#### `world_states`

```sql
create table world_states (
  world_state_id uuid primary key,
```

## 5. 旧到新的迁移策略

迁移目标不是“原样搬家”，而是“保留业务事实，放弃无价值缓存和派生壳”。

### 5.1 迁移分类原则

#### A 类：必须迁移

- `project.json`
- 原始上传文件与 `extracted_text.txt`
- 关键分析产物 JSON
- `archive_library.sqlite3` 中的档案与长期记忆
- `chapter_meta.sqlite3`
- `session.json`
- `worldline runtime.sqlite3` 中的动作、对话、session memory
- `llm_facility.sqlite3` 中的 provider/channel/binding 配置

#### B 类：一次性导入即可

- `story_graph.json`
- `story_graph.sqlite3` 对应图信息
- `prepare.sqlite3` 中仍与已存在 session 有引用关系的 prepare run / dossier
- 历史任务状态中“已完成/已失败”的摘要记录

#### C 类：不值得迁移

- `task_runtime.sqlite3` 的实时进度细节
- `llm_models` 的上游缓存列表
- `archive_sources`
- `story_graph.sqlite3` 作为独立文件本身
- `index.json`
- 未持久化完成的 SSE 临时事件流

#### D 类：只能重建

- 任何依赖旧 branch 语义的 projection
- 以旧 prompt/旧模块契约计算出的 context pack 缓存
- 已过时的 prepare event log 明细
- 基于旧 schema 生成的临时检索索引

### 5.2 分阶段迁移计划

#### Phase 0：冻结旧库结构并做只读快照

- 对 `backend/uploads/system/*.sqlite3` 做文件级快照。
- 对每个项目目录做只读快照。
- 记录每个源对象的 `path + mtime + sha256 + size`。
- 不在这一阶段修改旧系统任何写路径。

#### Phase 1：建立新库空 schema 与对象存储目录

- 初始化 PostgreSQL schema。
- 初始化对象存储 bucket：
  - `manuscripts`
  - `artifacts`
  - `drafts`
  - `reports`
- 初始化 Redis key namespace。

#### Phase 2：离线回填基础对象

先迁：

- `workspace`
- `project`
- `manuscript`
- `artifact`

原则：

- 每个旧项目目录映射为一个 `project`。
- 目录内所有 JSON/TXT/上传文件先入对象存储，再写 `artifacts` 或 `manuscripts`。

#### Phase 3：回填 canonical domain

回填：

- `entities`
- `entity_relationships`
- `archives`
- `memories`
- `memory_events`
- `chapter_cards`
- `chapter_history_items`

#### Phase 4：回填 worldline domain

回填：

- `worldline_sessions`
- `world_states`
- `timeline_events`
- `session_agents`
- `agent_state_versions`
- `agent_actions`
- `agent_dialogues`
- session episodic memory

#### Phase 5：回填配置域

回填：

- `llm_providers`
- `llm_channels`
- `llm_models` 只做最新一次同步快照，可选
- `llm_module_bindings`

#### Phase 6：双写期

新代码上线后：

- 旧 JSON / SQLite 写路径继续保留只读兼容。
- 新系统成为主写路径。
- 对关键事实做镜像校验，不允许 silent fallback。

双写只保留有限范围：

- project 状态
- archive / memory
- worldline session 当前状态
- finalized chapter
- llm binding

不做双写：

- `llm_models` 模型缓存
- prepare 临时事件
- draft SSE 临时事件

#### Phase 7：校验与切换

切换顺序：

1. 先切只读查询接口到新 projection。
2. 再切写接口到新 PostgreSQL。
3. 最后摘掉旧的 JSON / SQLite 主写逻辑。

## 9. 校验与切换规则

### 9.1 回填校验

至少执行这些校验：

- 项目数校验：旧 `project.json` 数量 == 新 `projects` 数量
- 文件数校验：旧 `files/*` 数量 == 新 `manuscripts` 数量
- 档案数校验：旧 `narrative_archives.json.archives` 总数 == 新 `archives` 数量
- 长期记忆数校验：旧 `archive_agent_memory` 总数 == 新 `memories` 中 `memory_layer in ('canon','candidate','experiment')` 数量
- 章节卡数校验：旧 `chapter_meta` 总数 == 新 `chapter_cards` 数量
- worldline session 数校验：旧 `session.json` 数量 == 新 `worldline_sessions` 数量

### 9.2 语义校验

- 随机抽样 20 个 archive，比对 `entity_name / importance_tier / template_key / payload`。
- 随机抽样 20 条 memory timeline，比对版本链和状态流转。
- 随机抽样 10 个 worldline session，比对 timeline 长度、agent 数量、action 数量、dialogue 数量。
- 随机抽样 10 个 finalized chapter，比对章节正文哈希和 chapter card 摘要。

### 9.3 切换门槛

满足以下条件才能切换：

- 行级数量校验全部通过
- 语义抽样无 blocker
- 新 projection 能完整支持 `/writer`、`/worldline`、`/archive-library`、`/llm-facility`
- 新写路径已覆盖 `ingest / archive review / worldline / draft finalize`

## 10. 最终判断

这次迁移不能走“继续堆 SQLite 和 JSON”路线。正确做法是：

- 把项目、档案、世界线、正文生成全部纳入同一个 PostgreSQL 事实模型。
- 把大文本和制品移到对象存储。
- 把 Redis 限定在缓存和协调层。
- 把旧系统里所有“像数据库的数据”从文件系统里剥离出来。

如果还保留当前的“目录 JSON 真源 + 多个 SQLite 各写各的”模式，后续 writer、worldline、memory review、draft workflow 只会继续相互污染，最终无法维护。
