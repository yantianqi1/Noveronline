# 15. API Contracts

更新时间：`2026-07-13`

## API 原则

公网 API 由 Go Control Plane 提供。Python Agent Runtime 不直接暴露公网。

原则：

- URL 中体现 tenant/project 上下文。
- Body 不信任 tenant_id。
- 所有响应有稳定错误格式。
- 长任务返回 `run_id`，不阻塞 HTTP 等完成。
- SSE 用于进度和 token stream。
- API 使用 OpenAPI 生成客户端。
- 旧 `/api/*` 语义全部有新 endpoint 或明确迁移替代。

## 错误格式

```json
{
  "error": {
    "code": "LLM_MODULE_UNBOUND",
    "message": "writer_reviewer 模块未绑定",
    "details": {},
    "request_id": "req_..."
  }
}
```

常见 code：

- `UNAUTHENTICATED`
- `AUTH_BACKEND_UNCONFIGURED`
- `AUTH_USER_NOT_FOUND`
- `AUTH_ACCESS_DENIED`
- `AUTH_LOOKUP_FAILED`
- `FORBIDDEN`
- `NOT_FOUND`
- `VALIDATION_FAILED`
- `QUOTA_EXCEEDED`
- `RESOURCE_LOCKED`
- `WORKFLOW_FAILED`
- `WORKFLOW_CANCEL_BACKEND_UNCONFIGURED`
- `SOURCE_FILE_NOT_UPLOADED`
- `SOURCE_FILE_UPLOAD_NOT_COMPLETABLE`
- `SOURCE_FILE_UPLOAD_NOT_WRITABLE`
- `SOURCE_FILE_OBJECT_NOT_FOUND`
- `SOURCE_FILE_STORAGE_VERIFY_FAILED`
- `PROJECT_OVERVIEW_BACKEND_UNCONFIGURED`
- `PROJECT_OVERVIEW_QUERY_FAILED`
- `LLM_MODULE_UNBOUND`
- `LLM_PROVIDER_ERROR`
- `SCHEMA_VALIDATION_FAILED`

`X-Request-Id` is treated as public correlation metadata, not trusted application input. The Go HTTP boundary preserves safe request ids made of ordinary correlation characters (`A-Z`, `a-z`, digits, `-`, `_`, `.`, `:`) up to 128 characters, but replaces missing, malformed, or high-risk values with a generated `req_...` id. Error envelopes, workflow starter inputs, admission metadata, and Temporal payloads must not echo request id headers containing prompt/body/content text, API keys, `credential_ref`, object keys, raw/source text, draft, or manuscript fragments.

## SaaS / Auth

```http

POST /v1/auth/signup
POST /v1/auth/password/change

DELETE /v1/auth/session
GET /v1/auth/sessions
DELETE /v1/auth/sessions
POST /v1/auth/session/jwt-rotation
POST /v1/auth/session/rotation
GET /v1/me
GET /v1/tenants
POST /v1/tenants
DELETE /v1/tenants/{tenantId}/sessions
```

`POST /v1/auth/signup` 是公开自助注册入口，严格接收 `display_name`、`email`、`password` 和 `project_title`，拒绝未知字段与尾随 JSON，并使用独立 `auth_signup` 限流类别。成功路径在一个 PostgreSQL 事务中创建 active user、bcrypt password credential、首次 hash-only session、`personal` 工作区、owner 工作区成员、首项目和 `project_owner` 项目成员；会话、工作区或项目任一步失败都必须整体回滚，不允许留下“账号已存在但注册失败”的半成功状态。成功返回与登录相同的公开 `user` / `active_tenants` / `active_projects` 结构，并设置 `HttpOnly`、`SameSite=Lax`、正 `Max-Age` 的 `mirofish_session` Cookie；staging/production 即使在 HTTPS 反代后通过容器内 HTTP 调用 API，也必须强制 `Secure`。重复邮箱返回 `REGISTRATION_EMAIL_CONFLICT`；响应和日志不得包含明文密码、bcrypt hash、原始 session、session hash、签名密钥或数据库错误。

`POST /v1/auth/login` is the W2-S5q production password login session issuance seam. It strict-decodes JSON body fields `email` and `password` only, but the route requires a configured password authenticator, configured `AuthSessionStore`, and nonblank `MIROFISH_AUTH_SESSION_SECRET` / `Config.SessionAuthSecret` before JSON decode. Without any of those dependencies it returns `AUTH_BACKEND_UNCONFIGURED` and must not call the authenticator, session store, or issue a cookie. The SQL authenticator lowercases/trims email for lookup, reads only active `users` joined to active `user_password_credentials`, compares the stored bcrypt `password_hash`, and then reuses the current-user reader to return the existing public current-user shape. Invalid email/password uses a stable public auth error and must not disclose whether the user or credential exists. Successful login signs the existing nonce-bearing `v2:<user_id>:<nonce>:<hex_hmac_sha256>` session token, persists only token hash/user/expiry/status metadata through `AuthSessionStore`, and only after persistence succeeds sets `Set-Cookie: mirofish_session=...` with `HttpOnly`, `Path=/`, `SameSite=Lax`, positive `Max-Age`, and `Secure` on HTTPS requests or whenever staging/production runs behind TLS termination. Public success/error responses must not include password, bcrypt hash, raw token, token hash, signing secret, nonce, API keys, encrypted credential material, `credential_ref`, object keys, drafts, manuscripts, prompt/provider response, or raw body/content. Malformed `/v1/auth//login` or `/v1/auth/login/extra` paths remain ordinary 404s and must not call the authenticator/session store or issue cookies. This is not signup, password reset, OAuth, MFA, JWT refresh lifecycle, refresh-token lifecycle/session renewal, route-wide auth middleware, or complete production auth.

`POST /v1/auth/password/change` is the P3-008 authenticated password-change and all-session invalidation slice. The exact route requires a configured `PasswordChanger`, configured `AuthSessionStore`, and nonblank `MIROFISH_AUTH_SESSION_SECRET` / `Config.SessionAuthSecret` before credential handling or JSON decode. It accepts exactly one signed Bearer credential or a signed `mirofish_session` cookie and never uses development `X-User-Id`; cookie requests must pass token-bound `X-CSRF-Token` before session validation or body decode. The presented session row must then be active, unexpired, and non-revoked through `ValidateSession`. The request strict-decodes only `current_password` and `new_password`, rejects trailing JSON, requires a 12-72 byte new password different from the current value, verifies the current bcrypt credential, and uses one guarded PostgreSQL statement to replace the hash and revoke all active sessions for that user. Concurrent credential changes fail closed through the old-hash guard. Success returns `204 No Content`; cookie-sourced success expires `mirofish_session`, while Bearer success does not mutate cookies. Missing dependencies, malformed/duplicate credentials, invalid CSRF/session/current password/body, DB failure, or malformed paths return stable public auth errors or ordinary 404 without clearing cookies or exposing password/hash/token/driver/provider/body content. This slice is not signup, password reset/recovery, password policy administration, OAuth, MFA, refresh-token lifecycle, session-management UI, or complete production auth.

`POST /v1/auth/dev-sessions` 和 `X-User-Id` actor fallback 默认都关闭。`cmd/api` 只有在 `MIROFISH_DEPLOYMENT_ENV=local` 且 `MIROFISH_ENABLE_DEVELOPMENT_AUTH=1` 时才设置 `Config.AllowDevelopmentAuth=true`；staging、production、缺失环境或仅设置其中一个条件都必须关闭。关闭时 dev-session 精确路由返回普通 `404`，伪造 `X-User-Id` 不能建立身份并返回 `UNAUTHENTICATED`。显式开启后的开发会话仍必须验证目标 active user，生成随机 nonce 的签名 session，仅持久化 token hash，并在持久化成功后签发安全 Cookie；该能力不得作为部署后的用户登录流程。

`GET /v1/auth/csrf-token` is the W2-S5i/W2-S5n cookie-session CSRF token seam. It requires a presented `mirofish_session` cookie, verifies the signed legacy `v1` or nonce-bearing `v2` token, and, when `AuthSessionStore` is configured, validates the matching active, unexpired, non-revoked `user_sessions` row before returning metadata-only JSON `{ "csrf_token": "..." }`. Missing/invalid cookie, missing secret, revoked/expired session, lookup failure, or malformed route remains fail-closed with stable public auth errors or ordinary 404 for non-exact paths. The response must not include the raw session token, token hash, signing secret, nonce, user id, API keys, encrypted credential material, `credential_ref`, object keys, drafts, manuscripts, prompt/provider response, or raw body/content. The CSRF token is derived from the verified token hash and signing secret and is not persisted as schema data. W2-S5n requires this token on unsafe actor-sensitive API routes when the credential source is the browser cookie and no `Authorization` header is present; Bearer and development `X-User-Id` paths remain non-cookie paths.

`DELETE /v1/auth/session` is the Wave 2 current-session revocation/logout seam. It requires a presented signed `Authorization: Bearer <token>` or `mirofish_session` cookie and must not use the development `X-User-Id` fallback. The endpoint verifies Bearer credentials through the shared legacy `v1`, nonce-bearing `v2`, or W2-S5s compact JWT verifier; when the credential source is the cookie, W2-S5i requires a valid `X-CSRF-Token` for the same token hash before `RevokeSession` or cookie clearing. Bearer revocation remains non-cookie and does not require CSRF. When `AuthSessionStore` is configured it then revokes only the matching active, unexpired, non-revoked `user_sessions` row by token hash before clearing the browser cookie. Missing, malformed, missing-secret, revoked, expired, lookup-failed, missing/invalid CSRF, or store-failed credentials return stable public auth errors, do not call the auth reader, do not fall back to a header actor, and do not clear the cookie. Nil session store preserves stateless dev compatibility by clearing a valid signed cookie after the cookie CSRF check passes. Successful response is `204 No Content` plus an expired `mirofish_session` cookie with `HttpOnly`, `Path=/`, `SameSite=Lax`, and `Secure` on HTTPS requests. Public responses/errors must not include the session token, JWT claim body, token hash, signing secret, nonce, user id, API keys, encrypted credential material, `credential_ref`, object keys, drafts, manuscripts, prompt/provider response, or raw body/content. Malformed `/v1/auth//session` or extra-segment logout paths remain ordinary 404s and must not call the session store or clear cookies. Production login completion, JWT refresh lifecycle, refresh/session renewal, production-grade browser cookie rotation/revocation UX, route-wide CSRF, and route-wide auth middleware remain follow-up work.

`GET /v1/auth/sessions` is the W2-S5o current-user session listing metadata seam. It requires a presented signed `Authorization: Bearer <token>` or `mirofish_session` cookie and a configured `AuthSessionStore`; it must not use development `X-User-Id` fallback and must not call `/v1/me` auth reader. Because it is a safe `GET`, cookie-sourced requests do not require `X-CSRF-Token` and must not mutate cookies. The DB-backed store uses the presented token hash only as an active/unexpired/non-revoked precondition and current-session marker before returning active session metadata. Successful response shape is `{ "sessions": [{ "session_id": "...", "status": "active", "expires_at": "...", "last_seen_at": "...", "current": true }] }`; it must not include raw token, JWT claim body, token hash, signing secret, nonce, user id, fallback actor, API keys, encrypted credential material, `credential_ref`, object keys, drafts, manuscripts, prompt/provider response, or raw body/content. Missing/malformed credential, missing store, inactive presented token, lookup/query/scan failure, or missing secret returns stable public auth errors without cookie mutation. Malformed `/v1/auth//sessions` or extra-segment session-list paths remain ordinary 404s and must not call the session store. This is not production login completion, JWT refresh lifecycle, refresh-token lifecycle, route-wide auth middleware, or production-grade session management UI.

`POST /v1/auth/session/access-token` is the W2-S5w current-cookie JWT Bearer access-token issuance seam. It is bodyless for trust purposes: the only accepted source is an existing nonblank `mirofish_session` cookie, and the endpoint must not accept `Authorization: Bearer`, development `X-User-Id`, body tenant, or body project as the source. It requires a configured `AuthSessionStore` and nonblank `MIROFISH_AUTH_SESSION_SECRET` / `Config.SessionAuthSecret`. The handler first verifies the old cookie signature/JWT to obtain `userID` and old token hash, then verifies cookie-bound `X-CSRF-Token` for that old hash before any session-store call, JWT signing, or persistence side effect. After CSRF passes, it calls `AuthSessionStore.ValidateSession` to require the old row to be active, unexpired, and non-revoked; then it signs a fresh compact HS256 JWT with the fixed `iss=mirofish-auth`, `aud=mirofish-api`, `sub`, fresh `sid`, `iat`, and `exp` claims; then it persists only `hashSessionToken(accessToken)` through `AuthSessionStore.CreateSession`. Successful response is written only after persistence succeeds and has shape `{ "access_token": "<compact jwt>", "token_type": "Bearer", "expires_at": "..." }`. The endpoint must not set, clear, or rotate browser cookies. Missing cookie, invalid cookie, missing secret, missing store, missing/invalid CSRF, inactive old row, lookup failure, signing failure, or create failure returns stable public auth errors and must not return a token or mutate cookies. Public errors must not expose the old cookie token, newly generated token on failure, JWT claim body, old or new token hash, signing secret, nonce/session id, fallback actor, body tenant/project, password, API keys, encrypted credential material, `credential_ref`, object keys, drafts, manuscripts, prompt/provider response, or raw body/content. Malformed `/v1/auth//session/access-token` or `/v1/auth/session/access-token/extra` remain ordinary 404s and must not call the actor resolver, session store, signer, or cookie side effects. This is not refresh-token lifecycle/session renewal, JWT refresh endpoints/lifecycle, OAuth/MFA, route-wide auth middleware, or complete production auth.

`POST /v1/auth/session/jwt-refresh` is the W2-S5x Bearer-only compact JWT renewal seam. It is bodyless for trust purposes: the only accepted source is exactly one `Authorization: Bearer <compact jwt>` header. It must not accept cookie-only requests, development `X-User-Id`, body tenant, body project, duplicate Authorization headers, or legacy `v1` / nonce-bearing `v2` Bearer session tokens. The endpoint requires a configured `AuthSessionStore` and nonblank `MIROFISH_AUTH_SESSION_SECRET` / `Config.SessionAuthSecret` before credential verification or store side effects. It verifies the compact JWT with the fixed `iss=mirofish-auth`, `aud=mirofish-api`, `sub`, `sid`, `iat`, and `exp` claims, signs a fresh compact HS256 JWT in memory, and then persists renewal only through `AuthSessionStore.RotateSession(oldHash -> newHash)`. `RotateSession` is the single DB side effect and must require the presented old JWT row to be active, unexpired, non-revoked, and owned by the same user before swapping hashes; the endpoint must not call `CreateSession`, multiply active sessions, set cookies, clear cookies, or use CSRF. Successful response is written only after rotation succeeds and has shape `{ "access_token": "<compact jwt>", "token_type": "Bearer", "expires_at": "..." }`. Missing/malformed/legacy credentials, missing secret, missing store, expired JWT, inactive old row, signing failure, lookup failure, or rotate failure returns stable public auth errors and must not return a token or mutate cookies. Public errors must not expose raw token, JWT claim body, old or new token hash, signing secret, nonce/session id, fallback actor, body tenant/project, password, API keys, encrypted credential material, `credential_ref`, object keys, drafts, manuscripts, prompt/provider response, or raw body/content. Malformed `/v1/auth//session/jwt-refresh` or `/v1/auth/session/jwt-refresh/extra` remain ordinary 404s and must not call the actor resolver, session store, signer, or cookie side effects. This is not refresh-token lifecycle/session renewal, OAuth/MFA, route-wide auth middleware, Web UI integration, or complete production auth.

`DELETE /v1/auth/sessions` is the W2-S5l current-user all-session revocation seam. It requires a presented signed `Authorization: Bearer <token>` or `mirofish_session` cookie, requires a configured `AuthSessionStore`, and must not use the development `X-User-Id` fallback. Cookie-sourced requests require a valid `X-CSRF-Token` for the presented token hash before any store call or cookie clearing; Bearer requests remain non-cookie and do not require CSRF. The DB-backed store must use the presented token hash as an active/unexpired/non-revoked precondition before revoking all active sessions for that same user, so a stale signed credential cannot revoke newer sessions. Missing store, missing/malformed credential, invalid CSRF, inactive presented token, lookup/store failure, or missing secret returns stable public auth errors and must not clear or replace cookies. Successful cookie requests return `204 No Content` plus an expired `mirofish_session`; successful Bearer requests return `204 No Content` without browser cookie mutation. Public responses/errors must not include the session token, JWT claim body, token hash, signing secret, nonce, user id, API keys, encrypted credential material, `credential_ref`, object keys, drafts, manuscripts, prompt/provider response, or raw body/content. Malformed `/v1/auth//sessions` or extra-segment all-session revocation paths remain ordinary 404s and must not call the session store or mutate cookies. This is not session listing, refresh-token lifecycle, production login completion, JWT refresh lifecycle, route-wide CSRF, or route-wide auth middleware.

`DELETE /v1/tenants/{tenantId}/sessions` is the W2-S5m admin tenant-wide session revocation seam. It requires a trusted actor context from the existing signed Bearer / `mirofish_session` / development actor resolver, authorizes tenant-scoped `tenant_session_manage` against the path tenant id before any session-store mutation, and requires a configured `AuthSessionStore`. The permission is allowed only for active tenant `owner` / `admin`; project role alone is not sufficient. The endpoint does not decode a body, does not trust body tenant/project fields, and does not clear or replace cookies on success or failure. Under W2-S5n, cookie-sourced requests must present `X-CSRF-Token` before actor resolver, session validation, authorizer, or session-store side effects; Bearer and development actor requests remain non-cookie paths. The DB-backed store revokes active `user_sessions` rows for users with active membership in the path tenant by writing only session status/revocation metadata. W2-S5u wires the Next project shell to this exact API through a tenant owner/admin-only server action that reads the HttpOnly cookie at action time, fetches CSRF server-side, calls the path tenant id, and deletes only the Next-side cookie after API success. Missing/malformed actor credentials, missing/invalid CSRF for cookie requests, denied authorization, missing store, lookup/store failure, or missing secret returns stable public auth errors and must not expose authorizer/store exception text. Public responses/errors must not include session tokens, JWT claim bodies, token hashes, signing secrets, nonce values, user ids beyond existing public actor context, API keys, encrypted credential material, `credential_ref`, object keys, drafts, manuscripts, prompt/provider response, or raw body/content. Malformed `/v1/tenants//{tenantId}/sessions`, `/v1/tenants/{tenantId}//sessions`, or extra-segment tenant-session paths remain ordinary 404s and must not call the actor resolver, authorizer, session validator, or session store. This is not session listing, audit expansion, refresh-token lifecycle, production login completion, JWT refresh lifecycle, or route-wide auth middleware.

`POST /v1/auth/session/rotation` is the Wave 2 current browser session rotation API seam. It requires an existing `mirofish_session` cookie and a configured `AuthSessionStore`; it does not accept `Authorization: Bearer` as the rotation source and must not use the development `X-User-Id` fallback. The endpoint verifies the presented cookie as legacy `v1` or nonce-bearing `v2`, then W2-S5i requires a valid `X-CSRF-Token` for the old token hash before signing a fresh token, calling the store, or issuing any replacement cookie. After CSRF passes, it signs a fresh nonce-bearing `v2` token, then asks the session store to atomically replace the old token hash with the new token hash only if the old row is active, unexpired, non-revoked and belongs to the same user. Only after the store update succeeds may the API set a replacement `mirofish_session` cookie with `HttpOnly`, `Path=/`, `SameSite=Lax`, positive `Max-Age`, and `Secure` on HTTPS requests; successful response is `204 No Content`. Missing cookie, invalid cookie, missing secret, missing/invalid CSRF, missing store, missing/expired/revoked old row, lookup failure, or store failure returns stable public auth errors and must not issue a replacement cookie. Public responses/errors must not include old or new session token, old or new token hash, signing secret, nonce, user id, API keys, encrypted credential material, `credential_ref`, object keys, drafts, manuscripts, prompt/provider response, or raw body/content. Malformed `/v1/auth//session/rotation` or extra-segment rotation paths remain ordinary 404s and must not call the session store or set cookies. W2-S5j wires this endpoint into an explicit Next project shell refresh action. W2-S5k adds an automatic project-shell trigger through same-origin `POST /api/auth/session/refresh`: browser JS only posts to the internal route with same-origin credentials and no body/header token material; the Next route reads the HttpOnly cookie server-side, fetches CSRF, calls this Go rotation endpoint, and sets a replacement browser cookie only after successful rotation. W2-S5t gates that automatic trigger with current-session public `expires_at` metadata from `GET /v1/auth/sessions`: the client receives only the expiry timestamp plus an enabled boolean, skips refresh when expiry is missing/invalid or more than 15 minutes away, and still lets the same-origin route own all cookie/CSRF handling. Automatic trigger failure leaves the cookie unchanged and returns only sanitized status. Refresh token lifecycle, JWT refresh lifecycle, backend session renewal semantics, and route-wide auth middleware remain follow-up work.

`POST /v1/auth/session/jwt-rotation` is the W2-S5v current browser session JWT-cookie migration seam. It requires an existing `mirofish_session` cookie, a configured `AuthSessionStore`, and a valid `X-CSRF-Token` for the presented old token hash before signing a compact JWT, calling the store, or issuing any replacement cookie. It does not accept `Authorization: Bearer` as the rotation source and must not use the development `X-User-Id` fallback. After CSRF passes, it signs a compact HS256 JWT with the existing fixed `iss=mirofish-auth`, `aud=mirofish-api`, `sub`, `sid`, `iat`, and `exp` claims, then asks the session store to atomically replace the old token hash with the JWT token hash only if the old row is active, unexpired, non-revoked, and belongs to the same user. Only after the store update succeeds may the API set a replacement `mirofish_session` cookie with `HttpOnly`, `Path=/`, `SameSite=Lax`, positive `Max-Age`, and `Secure` on HTTPS requests; successful response is `204 No Content` with no JSON token body. Missing cookie, invalid cookie, missing secret, missing/invalid CSRF, missing store, missing/expired/revoked old row, lookup failure, signing failure, or store failure returns stable public auth errors and must not issue a replacement cookie. Public responses/errors must not include old or new session token, JWT claim body, old or new token hash, signing secret, nonce/session id, fallback actor, API keys, encrypted credential material, `credential_ref`, object keys, drafts, manuscripts, prompt/provider response, or raw body/content. Malformed `/v1/auth//session/jwt-rotation` or extra-segment JWT rotation paths remain ordinary 404s and must not call the session store or set cookies. This is not refresh-token lifecycle/session renewal, JWT refresh endpoints/lifecycle, OAuth/MFA, route-wide auth middleware, or complete production auth.

`GET /v1/me` is the Wave 2 current-user seam. It requires a trusted actor context; missing or blank user context returns `UNAUTHENTICATED` before the auth reader is called. W2-S4c adds signed subject resolution for `Authorization: Bearer <token>` and `mirofish_session` cookie when `MIROFISH_AUTH_SESSION_SECRET` / `Config.SessionAuthSecret` is configured. The verifier accepts legacy `v1:<user_id>:<hex_hmac_sha256>` tokens signed over `v1:<user_id>`, W2-S5g `v2:<user_id>:<nonce>:<hex_hmac_sha256>` tokens signed over `v2:<user_id>:<nonce>`, and W2-S5s/W2-S5v compact HS256 JWT Bearer/cookie tokens with `alg=HS256`, `typ=JWT`, `iss=mirofish-auth`, `aud=mirofish-api`, required `sub` / `sid`, valid `iat`, and unexpired `exp`; JWT verification returns only `sub` plus `hashSessionToken(fullJWT)` and does not trust role/project claims. Bearer takes precedence over cookie, and cookie takes precedence over the development `X-User-Id` fallback. W2-S5d adds optional persisted-session validation: when `AuthSessionStore` is configured, a presented signed Bearer/cookie credential must validate HMAC/JWT signature and then match an active, unexpired, non-revoked `user_sessions` row by token hash before the actor is accepted. Missing, revoked, expired, lookup-failed, invalid, malformed, duplicate, or missing-secret presented credentials fail closed with sanitized `UNAUTHENTICATED` / auth error on actor/RBAC-sensitive known routes and must not fall back to `X-User-Id`, call the auth reader, call the authorizer, or proceed with protected side effects. The development `X-User-Id` fallback is allowed only when no Bearer/cookie credential is presented. Nil session store preserves the prior stateless HMAC/JWT signature behavior. Public `/healthz` and default unknown-route 404 remain public even if a stale or malformed credential is present. `/v1/me` does not require `X-Tenant-Id`, does not trust body tenant fields, and must not fabricate tenant/project memberships from request headers. The endpoint uses an injected auth reader and defaults to `AUTH_BACKEND_UNCONFIGURED` / HTTP 503 when no backend is configured. When `DATABASE_URL` is configured, `cmd/api` wires a DB-backed auth reader and session store: the reader reads active `users` public columns, active `tenant_memberships` joined to active `tenants`, and active projects visible through those active tenant memberships, while the session store reads/writes only session hash/status/expiry/revocation metadata. Project role is `project_members.role` when a row exists for the current user, otherwise it inherits the tenant membership role. Successful responses contain only public user metadata plus active tenant and project membership summaries in the Go response shape: top-level `user` with user id, email, display name and avatar URL, plus top-level `active_tenants` with tenant id/name/role/status and `active_projects` with project tenant id/project id/name/role/status. Missing or inactive users return `AUTH_USER_NOT_FOUND`; ordinary query/scan/rows/close/session-store failures return stable public auth errors. HTTP responses must not echo reader/session-store exception text containing prompt/body/content, API keys, encrypted credential material, `credential_ref`, object keys, raw/source text, token/JWT claim material, drafts, or manuscripts. Refresh-token lifecycle/session renewal, OAuth/MFA, route-wide auth middleware, and complete production auth remain follow-up work.

The Next project shell consumes `GET /v1/me` through a typed `getCurrentUser` Web API client. W2-S5b originally wired the project layout to read the browser `mirofish_session` cookie server-side and forward it to Go `/v1/me` as `Cookie: mirofish_session=...`; P5 browser privacy hardening now requires render-time project layout and `webApiContext()` reads to use the isolated required request-session adapter rather than public `next/headers` dynamic APIs, and cookie-backed Web API calls use the Node `http`/`https` transport rather than Next's patched global `fetch` so cookie material is not serialized into dev RSC/Flight payloads. ## LLM

```http
GET /v1/llm/settings
GET /v1/projects/{projectId}/llm/modules
POST /v1/llm/channels
PATCH /v1/llm/channels/{channelId}
DELETE /v1/llm/channels/{channelId}
POST /v1/llm/channels/{channelId}/sync-models
GET /v1/projects/{projectId}/llm/channels
GET /v1/projects/{projectId}/llm/channels/{channelId}/models
GET /v1/projects/{projectId}/llm/module-bindings
GET /v1/projects/{projectId}/llm/module-bindings/{moduleKey}/resolution
PUT /v1/projects/{projectId}/llm/module-bindings/{moduleKey}
DELETE /v1/projects/{projectId}/llm/module-bindings/{moduleKey}
GET /v1/projects/{projectId}/llm/activity?run_id={runId}&module_key={moduleKey}
GET /v1/projects/{projectId}/llm/usage?run_id={runId}&module_key={moduleKey}
GET /v1/projects/{projectId}/agent-traces/{traceId}/events
GET /v1/projects/{projectId}/agent-traces/{traceId}/events?include_full=true
POST /v1/projects/{projectId}/agent-traces/{traceId}/export
```

`GET /v1/llm/settings` returns a tenant-scoped sanitized LLM settings snapshot under `X-Tenant-Id`. W2-S4n requires tenant-scoped `llm_module_binding_manage` before the settings reader is called; this tenant-level permission uses the header tenant and resolved actor, does not require a project id, and is limited to active tenant `owner` / `admin`. The snapshot includes documented module registry metadata, tenant/platform-visible channel metadata, and tenant-default module bindings only. It must not return `api_key`, `encrypted_api_key`, `credential_ref`, raw provider payloads, prompt bodies, or sensitive settings keys. Without a configured DB-backed settings reader it returns `LLM_SETTINGS_BACKEND_UNCONFIGURED` instead of fabricating an empty successful settings page.

`GET /v1/projects/{projectId}/llm/modules` exposes the sanitized LLM module registry for the current tenant/project context. The registry covers Seed / Graph, Archive / Assets, Worldline, and Writer module keys, and returns public metadata only: `module_key`, `group`, `label`, and `description`. It must not include credentials, provider secrets, prompt bodies, `credential_ref`, or binding-specific settings.

`GET /v1/projects/{projectId}/llm/channels` and `GET /v1/projects/{projectId}/llm/channels/{channelId}/models` expose sanitized tenant/platform-visible catalog metadata for binding selection. They must not include `api_key`, `encrypted_api_key`, raw provider payloads, or internal `credential_ref`.

`POST /v1/llm/channels`, `PATCH /v1/llm/channels/{channelId}`, and `DELETE /v1/llm/channels/{channelId}` mutate tenant-owned channels only under `X-Tenant-Id`. W2-S4n requires tenant-scoped `llm_module_binding_manage` before create/patch body decode or delete/store side effects. Body tenant/project fields are not trusted for authorization. `api_key` is accepted only in request bodies, encrypted server-side into the supported `aes-256-gcm:v1:<iv>:<tag>:<ciphertext>` envelope before storage, and is never returned. Public channel responses include only sanitized channel metadata. Malformed double-slash or extra-segment channel mutation paths must remain ordinary 404s and must not trigger actor resolution, authorization, or channel store calls.

LLM Facility JSON decode validation failures return stable `VALIDATION_FAILED` envelopes with empty public `details`. Request decoder strings must not be echoed for channel create/update or project module binding upsert, because unknown fields and type errors can expose names such as `api_key`, `prompt`, `credential_ref`, `draft`, `manuscript`, or Go internal request field names. This does not change channel credential encryption, module binding validation, model sync, or runtime provider invocation semantics.

LLM Facility store/reader/sync errors return fixed public messages by error code at the Go HTTP boundary. Resolver, module binding, catalog, settings, channel, model sync, and telemetry implementations are not trusted to provide safe `error.Error()` text; public responses must not echo driver/provider/store exception strings containing prompt text, API keys, encrypted credential material, `credential_ref`, draft text, or manuscript text. Query/update/sync failures use stable messages such as `LLM module binding query failed`, `LLM module binding update failed`, `LLM catalog query failed`, `LLM settings query failed`, `LLM channel update failed`, `LLM model sync query failed`, `LLM model sync failed`, and `LLM activity query failed`. Structured business errors such as `LLM_BINDING_TARGET_NOT_FOUND`, `LLM_BINDING_NOT_FOUND`, `LLM_CHANNEL_NOT_FOUND`, and backend-unconfigured errors keep fixed public meanings without exposing backend exception text.

`POST /v1/llm/channels/{channelId}/sync-models` syncs models for an enabled tenant-owned channel under `X-Tenant-Id`. W2-S4n requires tenant-scoped `llm_module_binding_manage` before the model syncer, credential decrypt, or provider call. The API decrypts the stored credential server-side, calls the channel's OpenAI-compatible `/models` endpoint, upserts sanitized `model_id` / `owned_by` metadata into `llm_models`, and updates `llm_channels.last_sync_at` / `last_sync_status`. Provider failures update an explicit failed sync status and return a stable error envelope. Responses include the sanitized channel and model list only; they must not include `api_key`, `encrypted_api_key`, raw provider payloads, or internal `credential_ref`. Malformed double-slash or extra-segment sync paths must remain ordinary 404s and must not trigger actor resolution, authorization, channel store calls, model syncer calls, credential decrypt, or provider calls.

`PUT /v1/projects/{projectId}/llm/module-bindings/{moduleKey}` requires W2-S4a tenant owner/admin authorization before JSON payload decode or module binding store calls. It writes a project override only after validating the target channel/model belongs to the tenant or an allowed platform channel. Public responses never include `api_key`, `encrypted_api_key`, or internal `credential_ref`; the writer workflow receives `credential_ref` only in its internal Temporal payload.

The `settings` object on `PUT /v1/projects/{projectId}/llm/module-bindings/{moduleKey}` may include `max_concurrency` as a positive integer for module-specific runtime concurrency. The value is stored in `settings_jsonb`, returned only as sanitized binding metadata, and never carries credential material.

`DELETE /v1/projects/{projectId}/llm/module-bindings/{moduleKey}` requires W2-S4a tenant owner/admin authorization before module binding store calls. It deletes only the current tenant/project override for that module. It does not delete tenant defaults or platform defaults; after deletion, resolution falls back to the next configured binding or returns `LLM_MODULE_UNBOUND`. Public responses include only the sanitized deleted binding metadata and never include credential material.

`GET /v1/projects/{projectId}/llm/activity` and `GET /v1/projects/{projectId}/llm/usage` require `X-Tenant-Id` and read only tenant/project scoped telemetry. Activity responses expose public call metadata and sanitized error summaries only; the SQL read side treats `llm_activity.error_jsonb` as untrusted and recursively removes `api_key`, `encrypted_api_key`, `credential_ref`, `prompt`, `response`, `body`, `content`, `candidate_body`, `event_body`, `source_material`, `source_text`, `draft`, `manuscript`, and related high-risk fields before returning records. With a real `*sql.DB`, the SQL reader must run inside a read-only transaction that sets `app_set_tenant_context(tenant_id, NULL, false)` before querying RLS-protected `llm_activity` / `usage_events`; fake queryers used by unit tests may keep the plain query path. The HTTP response boundary repeats the same recursive sanitization over every Activity record returned by any telemetry reader implementation, so replacing the reader cannot bypass credential/prompt redaction. If an error payload cannot be parsed, the API returns a stable generic summary instead of the raw error string. Activity / Usage reader query failures return stable `LLM_ACTIVITY_QUERY_FAILED` / `LLM activity query failed` responses; SQL/driver exception text must not reach HTTP responses, even if it contains prompt text, API keys, encrypted credential material, or `credential_ref`. Usage responses aggregate only `usage_events.usage_type = llm_tokens` by unit/module/run; generic billing, storage, import, workflow, or other non-LLM usage events must not appear in the LLM Facility Usage API. Usage responses must not expose prompt/response bodies, API keys, encrypted credential material, `credential_ref`, source material, event bodies, drafts, or manuscripts.

`GET /v1/projects/{projectId}/agent-traces/{traceId}/events` requires W2-S4b membership-backed project read authorization before the trace reader. The default response remains redacted/public. `include_full=true` additionally requires `trace_full_access` based on the resolved active project role (`project_owner`, `owner`, `admin`, or `editor`) plus the existing full trace checker before any full payload can be read; raw tenant role alone must not authorize full trace, and project overrides such as `writer`, `analyst`, or `viewer` deny full trace even when the tenant role is elevated.

`POST /v1/projects/{projectId}/agent-traces/{traceId}/export` requires W2-S4b project read authorization before body inspection, strict JSON validation, trace reader calls, or audit writes. If the request asks for full export, including duplicate-key bodies where any top-level `include_full` is `true`, the API must run resolved-project `trace_full_access` and the existing full trace checker before strict validation, reader, and auditor. JSON decode validation failures still return stable `VALIDATION_FAILED` envelopes with empty public `details` after the relevant auth gates pass. Request decoder strings must not be echoed because unknown fields and type errors can expose names such as `api_key`, `prompt`, `credential_ref`, `draft`, `manuscript`, or Go internal request field names.

Worker-side DB-backed LLM Facility query failures must use stable public errors. A module binding query failure is `LLM_BINDING_QUERY_FAILED` with message `LLM module binding query failed`; a credential lookup query failure is `LLM_CREDENTIAL_QUERY_FAILED` with message `LLM credential query failed`. Public API responses, workflow status/events, runner results, and LLM Activity must not include raw SQL/driver exception text, even when the underlying exception contains prompt text, API keys, encrypted credential material, or `credential_ref`.

Worker-side LLM Facility resolution must include a non-empty provider id before credential lookup or provider invocation. Missing `provider` in a resolved binding returns `LLM_PROVIDER_ERROR` with message `resolved LLM module is missing provider`; runtimes must not decrypt credentials, call the model provider, write candidate data, or mark the provider call completed when this field is absent.

## Compatibility

旧 endpoint 不在公网长期保留。迁移期可做 adapter：

```text
old /api/project/seed/extract
  -> new POST /v1/projects/{projectId}/seed-runs

old /api/project/build-graph
  -> new POST /v1/projects/{projectId}/story-graph/builds

old /api/unified-assets
  -> new GET /v1/projects/{projectId}/assets

old /api/writer-agent/run
  -> new POST /v1/projects/{projectId}/writer-runs
```

## 验收清单

- OpenAPI 能生成 TypeScript client。
- 所有 mutating API 校验权限。
- 长任务 API 不同步阻塞到任务完成。
- SSE 支持断线重连。
- 错误格式稳定。
- 旧功能都有新 endpoint 映射。
