# 15. API Contracts

更新时间：`2026-07-07`

## API 原则

公网 API 由 Go Control Plane 提供。Python Agent Runtime 不直接暴露公网。

原则：

- URL 中体现 tenant/project 上下文。
- Body 不信任 tenant_id。
- 所有响应有稳定错误格式。
- 长任务返回 `run_id`，不阻塞 HTTP 等完成。
- SSE 用于进度和 token stream。
- API 使用 OpenAPI 生成客户端。
- 旧 `/api/*` 语义全部有新 endpoint 或明确迁移替代。

## 错误格式

```json
{
  "error": {
    "code": "LLM_MODULE_UNBOUND",
    "message": "writer_reviewer 模块未绑定",
    "details": {},
    "request_id": "req_..."
  }
}
```

常见 code：

- `UNAUTHENTICATED`
- `AUTH_BACKEND_UNCONFIGURED`
- `AUTH_USER_NOT_FOUND`
- `AUTH_ACCESS_DENIED`
- `AUTH_LOOKUP_FAILED`
- `FORBIDDEN`
- `NOT_FOUND`
- `VALIDATION_FAILED`
- `QUOTA_EXCEEDED`
- `RESOURCE_LOCKED`
- `WORKFLOW_FAILED`
- `WORKFLOW_CANCEL_BACKEND_UNCONFIGURED`
- `SOURCE_FILE_NOT_UPLOADED`
- `SOURCE_FILE_UPLOAD_NOT_COMPLETABLE`
- `SOURCE_FILE_UPLOAD_NOT_WRITABLE`
- `SOURCE_FILE_OBJECT_NOT_FOUND`
- `SOURCE_FILE_STORAGE_VERIFY_FAILED`
- `PROJECT_OVERVIEW_BACKEND_UNCONFIGURED`
- `PROJECT_OVERVIEW_QUERY_FAILED`
- `LLM_MODULE_UNBOUND`
- `LLM_PROVIDER_ERROR`
- `SCHEMA_VALIDATION_FAILED`

`X-Request-Id` is treated as public correlation metadata, not trusted application input. The Go HTTP boundary preserves safe request ids made of ordinary correlation characters (`A-Z`, `a-z`, digits, `-`, `_`, `.`, `:`) up to 128 characters, but replaces missing, malformed, or high-risk values with a generated `req_...` id. Error envelopes, workflow starter inputs, admission metadata, and Temporal payloads must not echo request id headers containing prompt/body/content text, API keys, `credential_ref`, object keys, raw/source text, draft, or manuscript fragments.

## SaaS / Auth

```http
GET /v1/me
GET /v1/tenants
POST /v1/tenants
GET /v1/tenants/{tenantSlug}
GET /v1/tenants/{tenantSlug}/members
POST /v1/tenants/{tenantSlug}/invites
PATCH /v1/tenants/{tenantSlug}/members/{userId}
```

`GET /v1/me` is the Wave 2 W2-S1 current-user seam. It requires a trusted actor context from `X-User-Id` in the current development transport; missing or blank user context returns `UNAUTHENTICATED` before the auth reader is called. It does not require `X-Tenant-Id`, does not trust body tenant fields, and must not fabricate tenant/project memberships from request headers. The endpoint uses an injected auth reader and defaults to `AUTH_BACKEND_UNCONFIGURED` / HTTP 503 when no real auth backend is configured. Successful responses contain only public user metadata plus active tenant and project membership summaries: user id, email, display name, avatar URL, tenant id/name/role/status, and project tenant id/project id/name/role/status. Reader errors are mapped to stable public messages such as `AUTH_USER_NOT_FOUND`, `AUTH_ACCESS_DENIED`, `AUTH_LOOKUP_FAILED`, or `VALIDATION_FAILED`; HTTP responses must not echo reader exception text containing prompt/body/content, API keys, encrypted credential material, `credential_ref`, object keys, raw/source text, drafts, or manuscripts. DB-backed membership lookup, session cookies/JWT, tenant/project picker, and route-wide RBAC enforcement remain follow-up Wave 2 work.

`GET /v1/projects/{projectId}/overview` requires `X-Tenant-Id` and returns a tenant/project scoped public Project Health rollup when `DATABASE_URL` is configured. The current Go read side sets app-role tenant context, aggregates sanitized counts from `source_files`, seed `workflow_runs`, active workflow metadata, latest failed workflow public summary (`run_id`, `workflow_type`, `error_code`, `updated_at`), the latest `project_readiness_snapshots` public columns, enabled `assets`, the latest `story_graph_snapshots` node/edge counts, `worldline_sessions`, `worldline_events`, `character_interaction_sessions`, `writer_runs`, `llm_activity`, `usage_events.usage_type = llm_tokens`, enabled LLM channels, enabled-channel model-sync status counts (`ok`, `failed`, `pending`, latest sync timestamp), valid bound LLM modules, and missing core creative LLM modules. It returns project id, derived status, source file count, seed run count, active workflow id/type/status, latest failed workflow id/type/error code/updated timestamp, readiness snapshot/run ids, readiness counts, cross-module public counts, LLM configuration public counts, LLM model-sync public counts, and an updated timestamp. It must not select or return source object keys, raw or parsed text, readiness report bodies, asset content, graph evidence snippets, worldline event bodies, character turn bodies, workflow error messages, prompt/response bodies, API keys, encrypted credential material, `credential_ref`, channel/model/provider/base URL details, drafts, or manuscripts. Model-sync health is derived only from existing `llm_channels.last_sync_status` / `last_sync_at` metadata and does not perform a live provider connectivity call. Without a configured DB reader it returns `PROJECT_OVERVIEW_BACKEND_UNCONFIGURED`; ordinary query/scan/rows failures return stable `PROJECT_OVERVIEW_QUERY_FAILED` / `project overview query failed` without echoing driver exception text. Next `/overview` now reads this aggregate contract through the typed Web API client and renders it in the Project Health header/panel; live provider connectivity calls, live cluster dependency checks, and deeper failure drilldown remain follow-up work.

## Uploads

```http
POST /v1/projects/{projectId}/uploads
PUT /v1/uploads/{uploadId}/object
POST /v1/uploads/{uploadId}/complete
GET /v1/projects/{projectId}/source-files
DELETE /v1/source-files/{fileId}
```

`POST /v1/projects/{projectId}/uploads` requires `X-Tenant-Id` and creates a metadata-only `source_files` admission row for a future object-storage-backed upload. The Go API trusts tenant/project context only from the header/path, accepts public file metadata (`filename`, `mime_type`, `size_bytes`, `sha256`, `purpose`), and returns sanitized source file metadata (`file_id`, `upload_id`, `project_id`, filename/mime/size/hash/purpose/parse status/timestamp). Upload admission only accepts source MIME types that the Seed parse path supports: `text/plain`, `text/markdown`, `text/x-markdown`, `application/x-markdown`, and `application/pdf`, with optional MIME parameters stripped before matching. Unsupported MIME values return stable `400 VALIDATION_FAILED` / `invalid source MIME type` before the store is called, and the DB-backed store also rejects them before insert. JSON decode validation failures return stable `VALIDATION_FAILED` / `invalid upload payload` without echoing decoder strings or unknown field names such as `api_key`, `prompt`, `credential_ref`, `draft`, or `manuscript`. It does not return `object_key`, presigned URLs, object credentials, raw file content, API keys, encrypted credential material, or fake parse results. Without a configured source file backend it returns `SOURCE_FILE_BACKEND_UNCONFIGURED`.

`PUT /v1/uploads/{uploadId}/object` requires `X-Tenant-Id` and streams source file bytes into the configured object storage backend after metadata admission. The HTTP boundary uses only header tenant and path upload id, loads internal object metadata plus current `parse_status` from `source_files`, and passes the request body to the object writer without trusting client-supplied object keys or project ids. Only `parse_status = pending` may write object bytes; `uploaded`, `parsing`, `parsed`, `failed`, `cancelled`, or unknown status returns `SOURCE_FILE_UPLOAD_NOT_WRITABLE` with HTTP `409 Conflict` before object writer calls, preventing completed or in-flight Seed sources from being overwritten. The MinIO/S3-compatible writer first spools the body to a temporary file, computes SHA-256, checks exact byte count and admitted `sha256`, and only then writes the object with server-side `sha256` metadata. Size/hash mismatch returns `SOURCE_FILE_OBJECT_PAYLOAD_MISMATCH` and must not write the object; storage write failures return `SOURCE_FILE_STORAGE_WRITE_FAILED`; missing object storage config returns `SOURCE_FILE_STORAGE_BACKEND_UNCONFIGURED`. The public success response is limited to `upload_id` and `status = stored`; it must not expose `object_key`, presigned URLs, object credentials, raw content, parsed text, API keys, encrypted credential material, or fake parse results. This endpoint does not mark `parse_status = uploaded`; clients must still call complete so object verification runs before Seed admission.

Next `/overview` now exposes a browser file picker backed by the typed Web API client for this endpoint. The Web action sends the selected `File` bytes with `X-Tenant-Id` / `X-User-Id` and path upload id only, surfaces the same sanitized success/error status, and still requires a separate complete action before Seed admission. The UI does not display object storage locators, credentials, raw/parsed text, or fabricated parse/segment status.

`POST /v1/uploads/{uploadId}/complete` requires `X-Tenant-Id` and acknowledges a previously admitted upload under the current tenant. The DB-backed implementation may update sanitized `source_files.parse_status` to `uploaded` only after object storage verification succeeds, then returns public source file metadata only. Without a configured object verifier / object storage backend, complete returns `SOURCE_FILE_STORAGE_BACKEND_UNCONFIGURED` and must not mark the upload completed. The DB-backed store reads the current `parse_status` before object verification and only allows `pending` / `uploaded` rows to continue; `parsing`, `parsed`, `failed`, `cancelled`, or any unknown status returns `SOURCE_FILE_UPLOAD_NOT_COMPLETABLE` with HTTP `409 Conflict` before verifier calls and before `UPDATE source_files`. The `UPDATE` itself is constrained to `parse_status IN ('pending', 'uploaded')`, so concurrent status changes cannot downgrade an already parsed/failed/cancelled source row back to `uploaded`. With verification configured and a completable status, the API verifies the internal `object_key` exists in the configured S3/R2/MinIO bucket and that object metadata matches the admitted file metadata. The verifier must request checksum metadata on `StatObject`; `StatObject.Size` must equal `size_bytes`, and `ChecksumSHA256`, user metadata, or object metadata must provide sha256 evidence matching admission `sha256`. Missing objects return `SOURCE_FILE_OBJECT_NOT_FOUND` with HTTP `409 Conflict`; missing/mismatched size or sha256 evidence returns `SOURCE_FILE_STORAGE_VERIFY_FAILED`; neither path marks the upload as completed. The response does not return `object_key`, presigned URLs, object credentials, API keys, encrypted credential material, raw file content, parsed text, object hash internals, or fake parse results. Missing uploads return `NOT_FOUND`; without a configured source file backend it returns `SOURCE_FILE_BACKEND_UNCONFIGURED`.

`GET /v1/projects/{projectId}/source-files` lists sanitized source file metadata under the current `X-Tenant-Id` and project scope. The response must not include `object_key`, raw file content, presigned URLs, object credentials, API keys, encrypted credential material, or parsed text payloads.

The source file store treats ordinary SQL/storage exceptions as untrusted. Create, complete, list, source lookup, Seed source validation, and object verification failures must return stable source-file error messages and must not echo driver/storage text containing prompt, API key, `credential_ref`, object key, source path, raw content, draft, or manuscript data. The HTTP boundary must apply the same fixed public-message mapping even when a replacement store returns an unsafe `AppError.Message`. Structured business errors such as `NOT_FOUND`, `SOURCE_FILE_NOT_UPLOADED`, `SOURCE_FILE_UPLOAD_NOT_COMPLETABLE`, `SOURCE_FILE_UPLOAD_NOT_WRITABLE`, and `SOURCE_FILE_OBJECT_NOT_FOUND` keep their explicit codes.

DB-backed source file reads/writes must set tenant context before touching RLS-protected `source_files` when using app-role connections. The Go source file store's create, complete, internal object metadata lookup, list, and Seed source validation paths use tenant-context-aware SQL when available; rows close / transaction commit failures are stable public source-file errors, and scan failures abort tenant-scoped rows/transactions before returning. This is required for the live upload -> object verification -> Seed admission chain and does not expose `object_key` or raw source content in public HTTP responses.

The current opt-in live harnesses validate the app-role/RLS upload -> object verification -> Seed admission prefix and Go API upload/complete -> Temporal worker -> Python parse/segment handoff against real Postgres and MinIO: source metadata admission, internal object metadata lookup, server-side object write, object verifier complete, Seed source validation, `workflow.queued` admission, extracted artifact object persistence, segment object persistence, and sanitized public Seed event replay all use trusted header/path/context scope. Public responses/events may include upload/source file ids for correlation, but remain free of object keys/raw text and source checksum material. Browser full-path upload, sequential reading/provider, semantic/LLM/OCR stages, and full Seed pipeline E2E remain separate pending checks. Tenant-scoped single-row DB scans must check row errors before close/commit and must not re-read driver row errors after successful close if the driver reports post-close `context canceled`; true close/commit failures remain stable source-file public errors.

## Workflows

```http
GET /v1/workflow-runs/{runId}
GET /v1/workflow-runs/{runId}/events
POST /v1/workflow-runs/{runId}/cancel
POST /v1/workflow-runs/{runId}/retry
```

SSE event:

```text
event: workflow.event
id: evt_...
data: {"type":"stage_progress","progress":42}
```

`GET /v1/workflow-runs/{runId}` reads `workflow_runs` under the current `X-Tenant-Id` context when the SaaS Postgres backend is configured. The response returns only public workflow metadata (`run_id`, `workflow_type`, `project_id`, `status`, `progress`, `message`, `error_code`, `error_message`, `created_at`, `updated_at`) and must not expose `result_jsonb`, writer options, prompt/body text, `credential_ref`, API keys, or encrypted credential material. Without a configured workflow read backend it returns `WORKFLOW_BACKEND_UNCONFIGURED`.

`GET /v1/workflow-runs/{runId}/events` reads persisted `workflow_events` under the current `X-Tenant-Id` context when the SaaS Postgres backend is configured. JSON clients may pass `?after_event_id={eventId}`; SSE clients may reconnect with `Last-Event-ID: {eventId}`. Responses only include events after that cursor, and a missing cursor returns `EVENT_CURSOR_NOT_FOUND` instead of silently replaying from the beginning. Public workflow event payloads may keep safe correlation metadata such as `source_file_id`, but must recursively remove credential-like and high-risk body/object reference fields such as `credential_ref`, `api_key`, `encrypted_api_key`, `prompt`, `response`, `body`, `content`, `raw_text`, `body_text`, `content_text`, `source_text`, `input_text`, `output_text`, `draft`, `manuscript`, `object_key`, `source_object_key`, `artifact_object_key`, `segment_object_key`, `source_sha256`, `sha256`, `hash`, and `checksum`; without a configured workflow event backend it returns `WORKFLOW_BACKEND_UNCONFIGURED`.

`POST /v1/workflow-runs/{runId}/cancel` requires `X-Tenant-Id` and carries actor/request context into the cancellation backend. When Temporal and the SaaS Postgres backend are configured, the API first reads the tenant-scoped `workflow_runs.temporal_workflow_id`, calls Temporal cancellation for that stored workflow id, then updates `workflow_runs` to `cancelled` and appends a `workflow.cancelled` event. If Temporal, Postgres, or a stored Temporal workflow id is missing it returns `WORKFLOW_CANCEL_BACKEND_UNCONFIGURED`; if Temporal rejects cancellation or persistence fails it returns a stable error and must not mark the run cancelled or emit success. The cancellation persistence payload must not include prompt/body text, `credential_ref`, `api_key`, or encrypted credential material.

`POST /v1/workflow-runs/{runId}/retry` requires `X-Tenant-Id` and carries actor/request context into an explicit retry backend. The route is available in the Go API, but the default backend is fail-closed and returns `WORKFLOW_RETRY_BACKEND_UNCONFIGURED`; it must not reset `workflow_runs.status`, emit retry events, or enqueue replacement work unless a real retry backend accepts the retry request. A future backend must preserve tenant scope and avoid exposing or reusing prompt/body text, `credential_ref`, API keys, or encrypted credential material through public responses.

## Seed

```http
POST /v1/projects/{projectId}/seed-runs
GET /v1/projects/{projectId}/seed-runs
GET /v1/projects/{projectId}/readiness
GET /v1/seed-runs/{runId}
GET /v1/seed-runs/{runId}/events
POST /v1/seed-runs/{runId}/cancel
POST /v1/seed-runs/{runId}/retry
```

`POST /v1/projects/{projectId}/seed-runs` requires `X-Tenant-Id` and accepts an `upload_id` plus analysis options. The Go API does not trust tenant context from the body; it injects tenant/project/user/request context into the Temporal `SeedPipelineWorkflow` payload and returns `202 queued` only after source-file validation succeeds and the Temporal backend accepts the workflow start. JSON decode validation failures return stable `VALIDATION_FAILED` / `invalid seed run payload` without echoing decoder strings or unknown field names such as `api_key`, `prompt`, `credential_ref`, `draft`, or `manuscript`. User-provided `options` are recursively sanitized before `SeedStarter`: body-provided `tenant_id` / `project_id`, credential/API key, prompt/response, body/content, source/material/raw payload, candidate/event body, draft, and manuscript fields are removed while safe public analysis options may remain. `TemporalSeedRunStarter` also recursively sanitizes `options` again before building the internal Temporal payload, treating hyphenated high-risk keys such as `api-key`, `credential-ref`, `raw-text`, `source-material`, and `candidate-event-body`, plus camelCase variants such as `sourceMaterial`, `candidateBody`, `candidateEventBody`, and `eventBody`, the same as their underscore variants, so internal callers that bypass the HTTP handler still cannot pass body-provided tenant/project authority, prompt/response/body/content/raw/source/material/candidate/event text, API keys, credential refs, drafts, or manuscripts into the Python worker handoff. Without a configured source file backend, Seed start returns `SOURCE_FILE_BACKEND_UNCONFIGURED` before calling `SeedStarter`, so the API cannot enqueue a source-less workflow shell. A configured Temporal seed starter also validates trusted Seed context and internal source handoff metadata before admission or `ExecuteWorkflow`: non-UUID tenant/project/upload/source ids or non-empty actor id return stable `VALIDATION_FAILED` / `seed workflow context is invalid`, while missing source metadata, unsupported source MIME, malformed `source_sha256`, or negative source size returns stable `VALIDATION_FAILED` / `seed source metadata is incomplete`; neither path may echo object key field names, object paths, MIME values, hashes, raw text, prompt/response bodies, credentials, drafts, or manuscripts. When both Temporal and the SaaS Postgres backend are configured, admission first advances the tenant/project/upload/source-file scoped `source_files` row from `uploaded` to `parsing`, then persists a tenant-scoped `workflow_runs` row and initial `workflow.queued` event before starting Temporal. The queued event may include `upload_id` and `source_file_id` public correlation metadata; in the DB-backed path, the `source_file_id` used for public metadata is derived from the same updated `source_files.file_id` row rather than caller event JSON, and the update must match the validated source id so the DB row and Temporal payload cannot diverge. The queued event must not include source object keys, source paths, raw/parsed text, prompt/response bodies, API keys, `credential_ref`, drafts, manuscripts, or encrypted credential material. DB-backed admission and start-failure compensation write paths validate UUID-shaped tenant/project/run/upload/source identifiers before SQL, reject invalid internal context as stable `VALIDATION_FAILED` / `seed admission context is invalid`, and set app-role tenant/project context before touching RLS-protected `source_files`, `workflow_runs`, and `workflow_events`. If no uploaded source row is advanced, the request returns stable `SOURCE_FILE_NOT_UPLOADED` and must not create a queued workflow row or enqueue a workflow. A configured Temporal seed starter must also have a Seed admission store; if the Temporal client is configured but the admission store is absent, it returns `WORKFLOW_BACKEND_UNCONFIGURED` / `seed admission store is not configured` before calling Temporal `ExecuteWorkflow`. Admission persistence failures return stable `WORKFLOW_ADMISSION_FAILED` and must not expose driver text or enqueue a workflow. If admission succeeds but Temporal `ExecuteWorkflow` fails, the public error is stable `WORKFLOW_FAILED` / `failed to start seed_pipeline workflow` and must not echo Temporal/client exception text, object keys, source paths, prompt/response bodies, API keys, `credential_ref`, drafts, or manuscripts. In the DB-backed path, that start failure is compensated by marking the admitted `workflow_runs` row `failed`, appending a sanitized `workflow.failed` event, and returning the same tenant/project/upload/source-file scoped `source_files.parse_status` from `parsing` to `uploaded`, so the API does not leave orphan queued/parsing state after a failed start. When the source row is released, the failed event may include row-derived `source_file_id` public metadata; if no row is released, failure metadata remains the stable workflow/upload/request/error fields only. Public workflow admission/failure metadata must not include raw file content, prompt/response bodies, drafts/manuscript text, `credential_ref`, API keys, object keys, source paths, or encrypted credential material. Without a configured workflow backend it returns `WORKFLOW_BACKEND_UNCONFIGURED` and must not fabricate seed analysis, segments, entities, or progress events.

With a configured source file backend, `POST /v1/projects/{projectId}/seed-runs` first validates that `upload_id` belongs to the current tenant/project in `source_files` and that `source_files.parse_status = uploaded`. Missing or cross-project uploads return `NOT_FOUND`; metadata-only uploads that have not been completed or rows already advanced beyond `uploaded` return `SOURCE_FILE_NOT_UPLOADED` with HTTP `409 Conflict`. In both cases the API must not start `SeedPipelineWorkflow`. After successful validation, the Go control plane passes internal source metadata (`source_file_id`, `source_object_key`, filename, MIME type, size, sha256) only inside the Temporal workflow payload for worker-side object storage reads. The Python parse worker treats the size/hash fields as guarded handoff metadata: when present, actual source object bytes must match before extraction continues; mismatch returns stable `SOURCE_FILE_OBJECT_INTEGRITY_MISMATCH` and must not expose expected hash, actual hash, object key, source path, raw text, prompt/response bodies, credentials, drafts, or manuscripts. The public HTTP response must not expose `object_key`, `source_object_key`, raw text, parsed text, prompt/response bodies, credentials, or hashes beyond the already sanitized source-file APIs.

Python Seed worker activity results and persisted workflow events are also public metadata boundaries. `parse_file_activity` and `segment_text_activity` must return stable error codes/messages for object storage env misconfiguration, source/artifact object read or write failure, source object integrity mismatch, UTF-8 decode failure, and segment metadata persistence failure. They must not echo object store, driver, writer, decoder, or integrity comparison details containing object keys, expected/actual hashes, prompt/source/body text, API keys, encrypted credentials, `credential_ref`, draft, or manuscript content. When a DB-backed source status writer is configured, `parse_file_activity` marks the tenant/project/source row `parsed` after the extracted text artifact is written, and attempts to mark it `failed` when the parse activity itself fails before segmentation. Both status transitions are constrained to rows currently in `parse_status = parsing`; if no `parsing` row is updated, or if SQL/driver execution fails, the writer rolls back and returns stable `SOURCE_FILE_PARSE_STATUS_UPDATE_FAILED` without exposing object keys, raw/parsed text, prompt, API keys, `credential_ref`, drafts, or manuscripts. This prevents parse workers from overwriting cancelled, already parsed, or otherwise concurrently moved source rows. `parse_file_activity` must not persist `seed.stage.completed` until the source status transition to `parsed` succeeds; a source status failure writes a sanitized `seed.stage.failed` event instead, so public event replay cannot show parse completed while the activity result failed. On parse failure paths, the failed event must also be recorded after the source row is successfully marked `failed`; if that status update fails, the failed event uses the same stable `SOURCE_FILE_PARSE_STATUS_UPDATE_FAILED` code as the activity result. Successful parse/segment activity results may carry object references internally for parse -> segment -> sequential-reading handoff, but public workflow events and API replay must not expose source, artifact, or segment object keys. `segment_text_activity` currently supports Chinese chapter headings, Markdown English `Chapter ...` headings, and unheaded paragraph-window segmentation; public workflow events may expose segment count, ids, order, chapter/title guesses, and strategy metadata, but must not expose segment object refs or raw text/content. Parse/segment object persistence is live-verified; richer semantic segmentation plus downstream LLM/OCR/browser E2E validation remain separate follow-up work. A segment object write failure is a structured `TEXT_SEGMENT_WRITE_FAILED` failure, not an unstructured activity crash.

When Python Seed parse/segment/sequential-reading/runtime-facts/global-aggregation/archive-candidates/index-assets/finalize uses DB-backed writers under app-role Postgres RLS, each writer must set tenant/project context before persisting public metadata, workflow status, structured canon, private seed analysis snapshots, candidate archive assets/memories, Seed asset/search projections, or project readiness snapshots: `workflow_events` for stage events, `workflow_runs` for admitted Seed running/terminal status, `project_text_artifacts` for extracted text object references, `source_files.parse_status` for parse lifecycle handoff, `text_segments` for segment references, `reading_passes` / `reading_segment_notes` for schema-validated notes, Seed/Canon target tables for structured facts, `seed_analysis_snapshots` for private global aggregation output, candidate `assets` / `archive_memories` / `archive_memory_events` for narrative archives, Seed `assets` / `global_search_index` for indexed seed assets, and `project_readiness_snapshots` for finalize readiness counts. SQL execute or commit failures must roll back the current connection and remain activity failures, not silent persistence success. Workflow status writes may update only same-tenant/project/run `workflow_runs.workflow_type = seed_pipeline`; running status does not write result/error material, completed result is public readiness metadata only, and failed status is stable public error code/message only. This is part of the upload -> complete -> Seed admission -> parse/segment/sequential-reading/runtime-facts/global-aggregation/archive-candidates/index-assets/finalize contract and does not make object keys, raw source text, parsed text, seed analysis bodies, archive candidate bodies, memory bodies, search document bodies, readiness report bodies, prompts, credentials, drafts, or manuscripts public API response fields.

The DB-backed global aggregation aggregate source is also part of this public metadata boundary. Before reading `segment_summaries` and structured fact counts it must set app-role tenant context, and ordinary query/driver failures must be reported as stable `SEED_AGGREGATE_SOURCE_QUERY_FAILED` without echoing SQL/driver exception text, prompt material, API keys, `credential_ref`, evidence, raw source text, drafts, or manuscripts.

`GET /v1/projects/{projectId}/seed-runs` requires `X-Tenant-Id` and lists only persisted `workflow_runs` where `workflow_type = seed_pipeline` under the current tenant/project. The SQL read side uses app-role tenant context when the queryer supports it, returns only public workflow metadata (`run_id`, `workflow_type`, `project_id`, `status`, `progress`, `message`, `error_code`, `error_message`, `created_at`, `updated_at`), and must not expose `result_jsonb`, source object keys, raw text, prompt/response bodies, `credential_ref`, API keys, or encrypted credential material. Ordinary query/scan/rows failures return stable `WORKFLOW_QUERY_FAILED` / `seed run query failed`, without echoing driver exception text. Without a configured Seed read backend it returns `WORKFLOW_BACKEND_UNCONFIGURED`.

`GET /v1/projects/{projectId}/readiness` requires `X-Tenant-Id` and reads the latest tenant/project scoped `project_readiness_snapshots` row when `DATABASE_URL` is configured. The SQL read side runs inside an app-role tenant context on real Postgres and selects only public snapshot metadata: `project_readiness_snapshot_id`, `project_id`, `run_id`, ready asset/entity/relationship/world-rule counts, `created_at`, and `updated_at`. It must not select or return readiness report bodies, prompt/response bodies, raw source text, search document bodies, API keys, encrypted credential material, `credential_ref`, drafts, or manuscripts. `GET /v1/writer-runs/{runId}` reads the persisted writer run under the current `X-Tenant-Id` context when the SaaS Postgres backend is configured. The response derives `trace_id` from the run id and returns only public run metadata (`run_id`, `trace_id`, `project_id`, `status`); it must not expose writer options, prompt content, `credential_ref`, API keys, or encrypted credential material.

`POST /v1/projects/{projectId}/writer-runs` requires `X-Tenant-Id` and resolves `writer_composer` through LLM Facility before admission. The HTTP boundary trusts tenant/project only from header/path context, recursively sanitizes user-provided `options` before `WriterStarter`, and removes body-provided `tenant_id` / `project_id`, credential/API key, prompt/response, body/content, source/material/raw payload, candidate/event body, draft, and manuscript fields. The server then adds trusted `module_key` and internal `llm_resolution` for the worker. JSON decode validation failures return a stable `VALIDATION_FAILED` envelope and must not echo decoder strings or unknown field names such as `api_key`, `prompt`, `credential_ref`, `draft`, or `manuscript`. DB-backed admission must also sanitize `writer_runs.options_jsonb` before persistence; public ids, `module_key`, and public turn summaries may remain as audit metadata. Public start responses return only run metadata and must not expose options, prompt/body text, `credential_ref`, API keys, encrypted credential material, draft text, or manuscript text.

`GET /v1/writer-runs/{runId}/events` reads persisted workflow events under the current `X-Tenant-Id` context. JSON clients may pass `?after_event_id={eventId}`; SSE clients may reconnect with `Last-Event-ID: {eventId}`. Responses only include events after that cursor, and a missing cursor returns `EVENT_CURSOR_NOT_FOUND` instead of silently replaying from the beginning. Next Writer may use event payloads internally for typed public tool cards, but public event/trace panels must not render raw payload JSON; they should show event metadata and payload key counts only so unsafe historical payloads cannot expose prompt/provider response/raw body/content/object keys/credentials/draft/manuscript prose through the UI.

`POST /v1/writer-runs/{runId}/cancel` requires `X-Tenant-Id` and carries actor/request context into the cancellation backend. If no cancellation backend is configured it returns `WORKFLOW_CANCEL_BACKEND_UNCONFIGURED`; it must not mark a run cancelled or emit success without a real backend accepting the cancellation request. When Temporal and the SaaS Postgres backend are configured, cancellation targets Temporal workflow id `writer_run_{runId}`, then updates `writer_runs` and `workflow_runs` to `cancelled` and appends a `writer.run.cancelled` workflow event. The cancellation persistence payload must not include prompt/body text, `credential_ref`, `api_key`, or encrypted credential material.

`GET /v1/projects/{projectId}/manuscript` requires `X-Tenant-Id` and reads tenant/project scoped manuscript metadata only. Without a configured manuscript reader it returns `MANUSCRIPT_BACKEND_UNCONFIGURED` and must not fabricate an empty successful manuscript. When `DATABASE_URL` is configured, the SQL reader sets tenant context and selects only `manuscript_blocks` public metadata: block id, project id, optional chapter id, optional source draft id, block order, status, word count, created timestamp, and updated timestamp. It must not select or return `content_text`, draft text, manuscript prose, prompt/provider response, API keys, encrypted credential material, `credential_ref`, object keys, or raw body/content. Query, scan, rows error, and close/commit failures return stable `MANUSCRIPT_QUERY_FAILED` / `manuscript query failed`; HTTP response sanitization also treats replacement-store metadata values and ids as untrusted.

`GET /v1/projects/{projectId}/manuscript/export` requires `X-Tenant-Id` and is a metadata-only export readiness/manifest endpoint, not a content export body. Without a configured manuscript reader it returns `MANUSCRIPT_EXPORT_BACKEND_UNCONFIGURED`; DB-backed query failure returns stable `MANUSCRIPT_EXPORT_QUERY_FAILED`. The only public format is normalized to `metadata_manifest`; content-looking `format=pdf|docx|txt` does not produce a file, prose, or fake artifact. The manifest may expose project id, format, status, block count, total word count, generated timestamp, and block id/order/word count metadata. It must not return `exported_at` unless a future real artifact path exists, and must not expose manuscript prose, draft text, `content_text`, prompt/provider response, API keys, encrypted credential material, `credential_ref`, object keys, or raw body/content.

`POST /v1/drafts/{draftId}/adoptions` requires `X-Tenant-Id` and is the explicit author action that moves one tenant-scoped `writer_drafts.status = candidate` row into manuscript metadata. The request may supply optional public `chapter_id` and `block_order`; `scene_id` override is rejected until `manuscript_blocks` has a scene-scoped target column. Without a configured backend it returns `DRAFT_ADOPTION_BACKEND_UNCONFIGURED` and must not fabricate manuscript success. When `DATABASE_URL` is configured, the SQL store runs under app-role tenant context, locks the candidate draft row, inserts a `manuscript_blocks` row from the private draft content internally, marks the draft `adopted` with `adopted_block_id`, and returns only public metadata (`draft_id`, `block_id`, `project_id`, `status`, optional chapter/scene ids, and `block_order`). The response and public errors must not expose draft text, manuscript text, `content_text`, prompt/response text, API keys, encrypted credential material, `credential_ref`, object keys, or raw body/content. Missing, already adopted, rejected, cross-tenant drafts, or failed result scanning fail closed and roll back instead of creating or committing a manuscript block.

`POST /v1/drafts/{draftId}/reviews` requires `X-Tenant-Id` and body `project_id`; it is the explicit author action for requesting a `writer_reviewer` pass on one tenant/project-scoped draft. The HTTP boundary ignores body tenant fields, rejects missing project scope before LLM resolution, sanitizes request options, resolves `writer_reviewer` through LLM Facility with that project scope, and returns `LLM_MODULE_UNBOUND` if no binding is configured. Without a configured DB-backed review store it returns `WRITER_REVIEW_BACKEND_UNCONFIGURED`; it must not fabricate review issues or report review success. When `DATABASE_URL` is configured, the SQL store verifies the draft belongs to the same tenant/project, writes only `workflow_runs`, sanitized `workflow.queued` event metadata that excludes user note/body text, and `draft_reviews.status = queued` metadata. Persisted review options may include public knobs such as `module_key` but must not include LLM routing snapshots, provider/base URL, channel/model ids, settings, `credential_ref`, prompt, or private text. `GET /v1/drafts/{draftId}/reviews` reads `draft_reviews` plus same-review/draft/project `draft_review_issues` public metadata only. Review responses and public errors must not expose draft text, manuscript text, `content_text`, prompt/provider response, API keys, encrypted credential material, `credential_ref`, object keys, raw body/content, user notes, or LLM provider payloads. Reviewer output remains candidate/review metadata; it does not adopt manuscript, rewrite canon, or mutate Worldline.

`GET /v1/llm/settings` returns a tenant-scoped sanitized LLM settings snapshot under `X-Tenant-Id`. The snapshot includes documented module registry metadata, tenant/platform-visible channel metadata, and tenant-default module bindings only. It must not return `api_key`, `encrypted_api_key`, `credential_ref`, raw provider payloads, prompt bodies, or sensitive settings keys. Without a configured DB-backed settings reader it returns `LLM_SETTINGS_BACKEND_UNCONFIGURED` instead of fabricating an empty successful settings page.

`GET /v1/projects/{projectId}/llm/modules` exposes the sanitized LLM module registry for the current tenant/project context. The registry covers Seed / Graph, Archive / Assets, Worldline, and Writer module keys, and returns public metadata only: `module_key`, `group`, `label`, and `description`. It must not include credentials, provider secrets, prompt bodies, `credential_ref`, or binding-specific settings.

`GET /v1/projects/{projectId}/llm/channels` and `GET /v1/projects/{projectId}/llm/channels/{channelId}/models` expose sanitized tenant/platform-visible catalog metadata for binding selection. They must not include `api_key`, `encrypted_api_key`, raw provider payloads, or internal `credential_ref`.

`POST /v1/llm/channels`, `PATCH /v1/llm/channels/{channelId}`, and `DELETE /v1/llm/channels/{channelId}` mutate tenant-owned channels only under `X-Tenant-Id`. `api_key` is accepted only in request bodies, encrypted server-side into the supported `aes-256-gcm:v1:<iv>:<tag>:<ciphertext>` envelope before storage, and is never returned. Public channel responses include only sanitized channel metadata.

LLM Facility JSON decode validation failures return stable `VALIDATION_FAILED` envelopes with empty public `details`. Request decoder strings must not be echoed for channel create/update or project module binding upsert, because unknown fields and type errors can expose names such as `api_key`, `prompt`, `credential_ref`, `draft`, `manuscript`, or Go internal request field names. This does not change channel credential encryption, module binding validation, model sync, or runtime provider invocation semantics.

LLM Facility store/reader/sync errors return fixed public messages by error code at the Go HTTP boundary. Resolver, module binding, catalog, settings, channel, model sync, and telemetry implementations are not trusted to provide safe `error.Error()` text; public responses must not echo driver/provider/store exception strings containing prompt text, API keys, encrypted credential material, `credential_ref`, draft text, or manuscript text. Query/update/sync failures use stable messages such as `LLM module binding query failed`, `LLM module binding update failed`, `LLM catalog query failed`, `LLM settings query failed`, `LLM channel update failed`, `LLM model sync query failed`, `LLM model sync failed`, and `LLM activity query failed`. Structured business errors such as `LLM_BINDING_TARGET_NOT_FOUND`, `LLM_BINDING_NOT_FOUND`, `LLM_CHANNEL_NOT_FOUND`, and backend-unconfigured errors keep fixed public meanings without exposing backend exception text.

`POST /v1/llm/channels/{channelId}/sync-models` syncs models for an enabled tenant-owned channel under `X-Tenant-Id`. The API decrypts the stored credential server-side, calls the channel's OpenAI-compatible `/models` endpoint, upserts sanitized `model_id` / `owned_by` metadata into `llm_models`, and updates `llm_channels.last_sync_at` / `last_sync_status`. Provider failures update an explicit failed sync status and return a stable error envelope. Responses include the sanitized channel and model list only; they must not include `api_key`, `encrypted_api_key`, raw provider payloads, or internal `credential_ref`.

`PUT /v1/projects/{projectId}/llm/module-bindings/{moduleKey}` writes a project override only after validating the target channel/model belongs to the tenant or an allowed platform channel. Public responses never include `api_key`, `encrypted_api_key`, or internal `credential_ref`; the writer workflow receives `credential_ref` only in its internal Temporal payload.

The `settings` object on `PUT /v1/projects/{projectId}/llm/module-bindings/{moduleKey}` may include `max_concurrency` as a positive integer for module-specific runtime concurrency. The value is stored in `settings_jsonb`, returned only as sanitized binding metadata, and never carries credential material.

`DELETE /v1/projects/{projectId}/llm/module-bindings/{moduleKey}` deletes only the current tenant/project override for that module. It does not delete tenant defaults or platform defaults; after deletion, resolution falls back to the next configured binding or returns `LLM_MODULE_UNBOUND`. Public responses include only the sanitized deleted binding metadata and never include credential material.

`GET /v1/projects/{projectId}/llm/activity` and `GET /v1/projects/{projectId}/llm/usage` require `X-Tenant-Id` and read only tenant/project scoped telemetry. Activity responses expose public call metadata and sanitized error summaries only; the SQL read side treats `llm_activity.error_jsonb` as untrusted and recursively removes `api_key`, `encrypted_api_key`, `credential_ref`, `prompt`, `response`, `body`, `content`, `candidate_body`, `event_body`, `source_material`, `source_text`, `draft`, `manuscript`, and related high-risk fields before returning records. With a real `*sql.DB`, the SQL reader must run inside a read-only transaction that sets `app_set_tenant_context(tenant_id, NULL, false)` before querying RLS-protected `llm_activity` / `usage_events`; fake queryers used by unit tests may keep the plain query path. The HTTP response boundary repeats the same recursive sanitization over every Activity record returned by any telemetry reader implementation, so replacing the reader cannot bypass credential/prompt redaction. If an error payload cannot be parsed, the API returns a stable generic summary instead of the raw error string. Activity / Usage reader query failures return stable `LLM_ACTIVITY_QUERY_FAILED` / `LLM activity query failed` responses; SQL/driver exception text must not reach HTTP responses, even if it contains prompt text, API keys, encrypted credential material, or `credential_ref`. Usage responses aggregate only `usage_events.usage_type = llm_tokens` by unit/module/run; generic billing, storage, import, workflow, or other non-LLM usage events must not appear in the LLM Facility Usage API. Usage responses must not expose prompt/response bodies, API keys, encrypted credential material, `credential_ref`, source material, event bodies, drafts, or manuscripts.

`POST /v1/projects/{projectId}/agent-traces/{traceId}/export` JSON decode validation failures also return stable `VALIDATION_FAILED` envelopes with empty public `details`. Request decoder strings must not be echoed because unknown fields and type errors can expose names such as `api_key`, `prompt`, `credential_ref`, `draft`, `manuscript`, or Go internal request field names. This does not change full trace permission checks, redacted/default trace reads, audit logging, or export semantics.

Worker-side DB-backed LLM Facility query failures must use stable public errors. A module binding query failure is `LLM_BINDING_QUERY_FAILED` with message `LLM module binding query failed`; a credential lookup query failure is `LLM_CREDENTIAL_QUERY_FAILED` with message `LLM credential query failed`. Public API responses, workflow status/events, runner results, and LLM Activity must not include raw SQL/driver exception text, even when the underlying exception contains prompt text, API keys, encrypted credential material, or `credential_ref`.

Worker-side LLM Facility resolution must include a non-empty provider id before credential lookup or provider invocation. Missing `provider` in a resolved binding returns `LLM_PROVIDER_ERROR` with message `resolved LLM module is missing provider`; runtimes must not decrypt credentials, call the model provider, write candidate data, or mark the provider call completed when this field is absent.
