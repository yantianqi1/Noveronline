# 项目现状 — 非程序员摘要

> 写给不写代码的人。技术词第一次出现时会解释。

## 1. 这个项目是什么

**MiroFish-Novel** 是一个帮助作家创作长篇中文小说的软件平台。它不是普通的打字工具，而是一个「多智能体（多个 AI 助手）分析与写作平台」：

- 你可以把一本已出版或草稿状态的小说（TXT、Word、PDF）上传进来；
- 系统会自动通读全文，抽出人物、组织、关系、伏笔、世界规则；
- 你可以指挥 AI 助手「按目前的世界观续写这一段」「查一下这个角色现在的状态」「检查这章有没有和前面矛盾」；
- AI 写出来的内容**不会自动进入正文**——你确认满意后，一键「采纳」才会变成正式稿件。这是刻意设计：AI 永远只提建议，作者掌握最终决定权。

一句话：**把「写作助手」从聊天窗口升级为拥有你整个故事档案的工作台。**

## 2. 当前主要功能

- **上传与通读（Seed Pipeline）**：上传小说后，系统分段精读、生成摘要、抽取人物/规则/时间线候选，再汇总成结构化知识。
- **故事档案库（Assets）**：人物档案、世界观、规则、伏笔、素材统一存放，可搜索（语义搜索 + 关键词混合），可勾选「常驻规则」让 AI 每章都遵守。
- **故事图谱（Story Graph）**：人物关系、组织关系画成一张可拖拽的图。
- **世界线（Worldline）**：单世界剧情推演——设定一个目标，让 AI 模拟故事走向，产出一系列「剧情事件」，作者可以采纳为剧情时间线。
- **写作台（Writer）**：主界面是连续稿件文档 + 右侧常驻 AI 协作者。输入要求 → AI 先查资料（你能看到它查了什么、引用了哪些设定）→ 生成候选稿 → 流式显示 → 你采纳或要求修改。
- **审校（Reviewer）**：独立的 AI 审校模块，检查文风、连续性、重复。
- **角色互动（Character Console）**：与单个角色对话模拟，产出角色提案。
- **计划与工具**：书籍计划、去重检查、禁用词、导出（TXT/Markdown 等）。

## 3. 当前用户使用流程

1. 注册/登录（浏览器页面）。
2. 创建一个小说项目，上传小说文件。
3. 等待系统通读完成（后台任务，界面显示进度）。
4. 在「图谱/档案」页查看抽取结果，修正或采纳候选内容。
5. 进入「写作台」：左侧是章节/稿件，右侧是 AI 协作者对话框。
6. 输入写作要求 → 观察 AI 检索资料的步骤 → 候选稿流式出现 → 点击「采纳」进入正文 → 继续下一段。
7. 写完后用「审校」检查，最后「导出」。

## 4. Pi Agent 在项目中扮演什么角色

「Pi Agent」是这个项目使用的 AI 助手技术底座（一个开源 SDK，类似给 AI 装上了「能自己查数据库、自己调用工具」的能力）。

项目里共有 **3 个 Pi Agent 程序**、**25 个 Agent 工具**：

| Agent | 干什么 | 有多少个工具 |
|---|---|---|
| Writer（写作） | 查资料 → 写正文 → 检查矛盾，5 个子阶段 | 13 个 |
| Analysis（通读分析） | 读小说分段、写分析笔记、提取候选人物/规则 | 7 个 |
| Worldline Cast（选角） | 为剧情推演挑选参与角色 | 5 个 |

「工具」= AI 可以主动调用的功能，比如「搜索设定」「读世界规则」「查角色档案」。AI 会自己决定调哪个、调几次；每一步都会显示给用户看。

## 5. 哪些功能由普通代码完成（不需要 AI）

- 用户注册/登录、权限控制、多租户隔离（每个用户只能看自己的数据）
- 文件上传、PDF 转文字、存储
- 章节/场景/稿件的增删改查、版本控制
- 事件流、任务状态机、失败重试、并发锁
- 用量统计、配额控制（防止 AI 调用烧钱失控）
- 数据库搜索、向量检索（语义搜索的「索引」部分）

## 6. 哪些功能由模型（LLM）完成

- 精读小说并产出摘要、人物、规则候选（有 AI 参与，最终由作者采纳）
- 剧情推演、角色对话模拟
- 写作：按「写作简报 + 检索到的设定」生成正文
- 审校：找矛盾、查重复、评文风
- 重排检索结果（让最相关的设定排前面）

## 7. 哪些功能由 Agent 工具完成

AI 不直接「看到」你的整个数据库，而是通过工具按需查询：

- 查项目信息、章节场景信息
- 语义搜索设定/前文（带引用来源）
- 查世界规则、角色档案（只读）
- 查故事图谱邻居关系、世界线路径、现有手稿
- 融合多路检索结果（去重排序）
- 分析 Agent 额外有：读写工作区文件（受路径白名单限制）、保存候选
- 选角 Agent 有：提交选角结果

**注意**：所有工具要么只读、要么只写「候选区」，没有任何工具能直接改写你的正式正文——这由作者「采纳」动作触发，且由普通代码完成。

## 8. 当前最重要的架构特点

1. **四层结构**：浏览器（Next.js）→ Go 控制面 API → Temporal 任务队列 → 三种运行时（Pi TS 运行时、Python 运行时、Legacy 参考）。AI 调用全部异步化：你发出请求，立即得到任务号，界面轮询进度。
2. **LLM 设施（LLM Facility）**：所有 AI 调用必须通过统一的「渠道/模型/模块绑定」体系，密钥加密存储、调用前预留配额、并发有锁、用量全部记账。禁止任何绕过它的调用。
3. **候选/正式分离**：AI 产出永远先落「候选」（candidate），只有用户动作才升级为「正式」（canon）。这是全系统的硬约束。
4. **多租户 + RLS**：每个数据库查询都带租户/项目上下文，数据库层面强制隔离。
5. **事件流**：AI 的每个步骤（检索开始、工具完成、正文 token）都写进事件表，前端据此渲染进度，页面刷新不丢状态。

## 9. 当前最明显的风险和技术债

1. **单 Go 文件过大**：`server.go` 约 1 万行，路由/handler 高度集中，维护成本高。
2. **前端用轮询而非长连接**：900ms 轮询 + 100 条/页游标，实时性一般、请求量大；后端已支持 SSE 但前端未用（这是「有实现未接通」的典型）。
3. **Legacy 双轨**：`backend/`（旧 FastAPI，8.9 万行）仍保留作迁移参考，且有未授权的 Legacy 数据导入 gate（MAIN-100），长期是维护负担。
4. **Agent 工具执行靠活动层透传**：工具执行发生在 Temporal 活动内，工具调用结果通过 `executeTool` 闭包回传；链路长，排障需要三端（Web/Go/Pi）日志对照。
5. **Pi SDK 版本较旧**（0.80.3），当前项目未使用 Pi 的 Extension/Skill/RPC 能力，未来升级有迁移成本。
6. **系统提示词大量内嵌在代码里**（TS 字符串拼接），修改提示词需要改代码发版，没有提示词管理界面。
